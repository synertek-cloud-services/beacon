# Beacon — CLAUDE.md

Self-hosted RMM platform, originally built for Synertek Cloud Services (developed by CodeNexus), now open-sourced under AGPL-3.0. Monorepo: Go agent, Cloudflare Workers backend, Vue 3 dashboard. See `README.md` for the human-facing overview and self-hosting quick start — this file is the AI-assistant-facing architecture/convention reference.

For current session-by-session status, recent decisions, and open follow-ups, see `PROJECT_LOG.md`.

**Terminology**: what the schema/API calls "Company" (`companies` table, `company_id` FK — renamed from `tenants`/`tenant_id`) is a client of the MSP running Beacon. "Location" (`company_locations`, née `tenant_locations`) is a lightweight address/contact sub-record under a Company — an office, not a scoping concept. Devices, Policies, Jobs, etc. all scope directly to **Company**, never Location. The many-to-many *targeting* tables (`policy_companies`, `component_companies`, `dashboard_companies`, `maintenance_policy_companies`, `patch_policy_companies` — originally `*_sites`) and the "Add Company flyout" UI pattern built on them (originally the "Add Company flyout") were renamed in a separate follow-on PR after the core Company rename, once it was confirmed nothing about them needed to stay distinct from "Company" — see the "Policy Targeting" and "Components/Job System" sections below for the current state. `.sf-*`/`.tf-*` remain the CSS class *prefixes* for these flyouts (unrenamed — arbitrary, non-semantic short codes, not worth touching).

**Local full-stack testing gotchas** (hit repeatedly enough to be worth writing down):
- `dashboard/vite.config.ts` already proxies `/v1` → `http://localhost:8787` — for local `pnpm dev` + `wrangler dev` testing, **don't** set `VITE_API_URL` at all (leave it unset so `api.ts`'s `baseUrl` stays `''`/relative). Setting it to `http://localhost:8787` directly makes the browser issue real cross-origin fetches, which the worker's CORS allowlist (hardcoded to exactly `http://localhost:5173`, see CORS below) will reject for any other local port — a real dead end hit while testing the Job scheduling work, cost real time before realizing the proxy already existed and made the override actively harmful.
- To manually fire the cron locally (needed to test anything in `scheduled()`, e.g. `dispatchDueScheduledJobs`/offline alerts): `curl "http://localhost:8787/cdn-cgi/handler/scheduled"` against a plain `wrangler dev` — no `--test-scheduled` flag needed, that flag only changes the startup banner's messaging, not whether the endpoint exists.
- A backgrounded `wrangler dev` from an earlier session can be left listening on 8787 while completely hung (accepts the TCP connection, never responds — `ss -ltnp` shows it bound, but every request times out). Symptom looks like "the port is busy" (a fresh `wrangler dev` fails to bind) rather than "nothing's listening" (`curl` would connection-refuse, not time out) — check `ss -ltnp | grep 8787` and kill the stale `workerd`/`wrangler` process tree before assuming something's wrong with a new change.
- **`cd dashboard && npx vue-tsc --noEmit` alone can silently check zero files and report false success** — `dashboard/tsconfig.json` is a solution-style config (`"files": []` + `"references"` to `tsconfig.app.json`/`tsconfig.node.json`), and plain `--noEmit` doesn't reliably walk project references the way `-b` (build mode) does. Caught for real during the tenant→company rename: `--noEmit` reported a fully clean dashboard even with genuinely broken imports and an unambiguous injected type error (`const x: string = 12345` inside a real `<script setup lang="ts">` block) present. `vue-tsc -b` (matching this project's own `package.json` build script) is the command that actually type-checks — use that, not `--noEmit`, whenever verifying dashboard changes are real. Clearing `node_modules/.tmp/*.tsbuildinfo` first rules out a stale incremental-build cache if results still look suspicious.

## Self-hosting config (not secrets, but org-specific — gitignored with `.example` templates)

`worker/wrangler.toml` and `dashboard/.env.production` are gitignored (real values are Synertek's own domain/D1 database, not committed for a public repo). Tracked `.example` counterparts (`worker/wrangler.toml.example`, `dashboard/.env.production.example`) hold placeholder values — anyone self-hosting copies the `.example` file and fills in their own domain/database ID. `[[r2_buckets]]` (`LOGOS` binding, added for branding logo uploads — see Branding below) needs R2 enabled on the Cloudflare account first (a one-time manual dashboard step, not something an API token can do) and the bucket created via `wrangler r2 bucket create <name>` before `wrangler deploy`/`--remote` migrations will resolve it — local `wrangler dev` auto-emulates R2, no real bucket needed there. `worker/wrangler.toml`'s `[vars]` block (`ALLOWED_ORIGIN`, `PAGES_PREVIEW_SUFFIX`) drives the CORS allowlist in `worker/src/index.ts` — don't hardcode a domain back into `index.ts`. `[vars]` also holds `WORKER_URL` (this worker's own public origin) — used by `sessions.ts` to build absolute agent/client WebSocket URLs. Deliberately a configured value rather than derived from the incoming request's own URL: with a `[[routes]]` custom-domain block present (as production's is), `c.req.url` reflects the production route even under `wrangler dev`, which previously caused local-dev remote-shell sessions to silently dial out to the real production worker instead of the local one — found and fixed during the Remote Shell session below.

## Architecture

**Worker** (`worker/src/`)
- Framework: Hono on Cloudflare Workers
- Database: Cloudflare D1 (SQLite) via Drizzle ORM (`worker/src/db/schema.ts`)
- Cron: runs every 2 minutes (`*/2 * * * *`) — evaluates offline alerts
- Durable Object: `SessionRelay` for shell/TCP tunnel sessions — see "Remote Shell / session system" below
- All admin routes under `/v1/admin/*`, `/v1/auth/*`, and `/v1/sessions*` require `Authorization: Bearer <token>` — either a real user session token or the `ADMIN_SECRET` break-glass token, resolved by `requireUser` (see Auth System below)
- CORS allows: production domain, localhost:5173, `*.beacon-dashboard-6f4.pages.dev` — must be explicitly enabled per route prefix (`app.use('/prefix/*', corsMiddleware)` in `index.ts`); `/v1/sessions` was missing from this list entirely until this session, since nothing had ever called it from a browser before

**Agent** (`agent/`)
- Module: `github.com/synertek-cloud-services/beacon/agent` (matches the GitHub org this repo is published under)
- Check-in interval: 60 seconds
- Metrics sent on every check-in: hostname, OS, uptime, disk_free_bytes, disks[] (multi-drive), cpu_percent, memory_percent, detected_class, av_status, av_product
- Check-in request also carries `pending_{file_size,ping,process,service}_results`; response carries `{file_size,ping,process,service}_checks` — see "Assign → measure → report pattern" below
- Audit (full inventory snapshot) fires 5 min after startup, then every 24 h, or on `run_audit` command
- Unknown command types are silently ignored for forward compatibility
- New fields added to `Metrics` must remain optional (old agents won't send them)
- Internal packages worth knowing: `diskutil` (shared multi-drive enumeration between check-in and audit), `filesize`, `pingutil`, `procutil`, `svcutil` — each is a small `Find`/`Measure`/`Ping` function following the same shell-out-or-gopsutil convention as the older `audit` package's AV/BIOS collectors
- `agent/internal/usersession` (Windows-only, `usersession_other.go` no-op stub elsewhere) — `RunAsSession(sessionID, exe, args)` launches a process in a given logged-in user's own session/environment from the agent's SYSTEM-context service process (`WTSQueryUserToken` → `DuplicateTokenEx(TokenPrimary)` → `CreateEnvironmentBlock` → `CreateProcessAsUser`). `RunAsActiveUser(exe, args)` is a thin console-session-only wrapper kept for `agent/tools/usersessiontest` and anything else that genuinely only cares about the console. `ActiveSessions()` (`WTSEnumerateSessions`, filtered to `WTSActive`) enumerates *every* currently-active session, not just the console one — the primitive that actually makes RDS/AVD/Windows 365 work (see below), since console-only session targeting misses all three: RDS has many concurrent non-console sessions, and AVD/Windows 365 have *no* console session at all, ever, even for a single user. Built as a standalone, reusable primitive after "the agent is headless" had separately blocked three different asks (Job System's declined "run as a logged in user," Patch Management's declined reboot-prompt, and implicitly anything else wanting to show a signed-in user something) — deliberately shipped with **no consumer wired up yet**, on its own, so its security-sensitive review surface (token/handle lifecycle) stayed small and independently auditable during that first pass. All three original consumers are now built: the tray (below), Patch Management's reboot prompt (below), and Job System's execution context (Components/Job System section). Doesn't expand what Beacon can already do — every command already runs as SYSTEM, strictly more powerful than any user's own context; this only changes *whose* context a launch happens in. `ErrNoActiveSession` (from `RunAsActiveUser` specifically) is the expected, common case (nobody has ever logged into the console, or a server with no interactive session) — always a no-op for callers, never a surfaced failure. **Locking the screen does not trigger this** — `WTSGetActiveConsoleSessionId` still returns the same session and `WTSQueryUserToken` still succeeds, since locking never disconnects the session; a launched process would just sit behind the lock screen until unlock.

**Verified against real hardware** (`agent/tools/usersessiontest`, a throwaway SYSTEM-context verification tool matching the `tools/sign`/`tools/verify` convention — run as a one-shot `SYSTEM`-user scheduled task, since `WTSQueryUserToken` needs the "Act as part of the operating system" privilege a plain Administrator session doesn't have): the core, actually-risky path works — launching a process in a real logged-in user's session from SYSTEM via the duplicated-token path genuinely succeeds. The `ErrNoActiveSession` fallback was **not** separately reproduced on hardware — the only way to trigger it live is a full logoff or testing before any login has ever happened, both disruptive on a machine in active use — and wasn't pursued given it's a single documented Windows API sentinel check (`WTSGetActiveConsoleSessionId() == 0xFFFFFFFF`), low-risk enough not to need a live reproduction the same way the impersonation path did.
- `agent/cmd/beacon-tray` (Windows-only) — a tray icon helper, and the first real consumer of `usersession`. Staged the same way `usersession` itself was. **Step 1** shipped the tray binary alone (`fyne.io/systray`, this codebase's first GUI-toolkit dependency; icon at `assets/icon.ico`, generated from the existing `dashboard/public/brand-mark.svg` — note the source SVG's non-zero `viewBox` origin (`138 23 240 418`) tripped up `oksvg`'s `SetTarget`/ViewBox-offset handling during generation, worked around by normalizing the SVG to a `0 0 …` viewBox first rather than trusting the library's offset math), a static, non-interactive menu (version label + a "Visit Dashboard" link), deliberately **no Exit item** (the process is meant to be supervised/relaunched, not dismissed). Verified real-hardware: both a direct launch and one via `usersession.RunAsActiveUser`'s impersonated path.
- **Step 2 — the real launch lifecycle** (all in `agent/internal/service`, no new package, no signature change to exported `service.Run()`): `EnsureTrayRunning()` (`tray_windows.go`, `tray_other.go` no-op stub) extracts the embedded `beacon-tray.exe` bytes (`//go:embed embedded/beacon-tray.exe` — a real, checked-in binary, refreshed by `scripts/publish-agent.mjs`'s new pre-build step right before the main 5-target loop, same `-trimpath` reproducibility requirement as the main binary since these bytes become part of it) to `installDir\beacon-tray.exe` if missing/stale, then launches or relaunches per session (see multi-session note below) whose tracked PID (package-level `map[uint32]uint32` session→PID state, `OpenProcess`+`GetExitCodeProcess`-checked for liveness) isn't alive. Called from three places: once at agent startup (`main.go`, next to `Reharden()`), once per 60s check-in loop tick (the actual resilience net — catches a crashed/killed tray or a missed session event, no separate ticker needed), and from a new `SERVICE_CONTROL_SESSIONCHANGE`/`WTS_SESSION_LOGON` hook in `runner_windows.go`'s `Execute()` (`svc.AcceptSessionChange`, run in its own goroutine so it can't block the control-request loop) — the hook is a latency optimization for near-instant appearance on login, the check-in tick is what actually guarantees correctness. `SetAgentVersion()` is separate, deliberately-package-level state (not a parameter) specifically so `EnsureTrayRunning()` has one uniform, no-argument signature callable from all three sites, including the hook inside `runner_windows.go` which has no access to `main.go`'s locals. `--dashboard-url` is deliberately never passed — the agent only knows its own worker URL, not the dashboard's (a different host in production), and there's no existing mechanism for it to learn that; the tray's "Visit Dashboard" item is already conditional on the flag being set, so it just doesn't appear rather than risking a guessed-wrong URL. `usersession.RunAsActiveUser` gained a small additive signature change for this — it now returns the launched PID (previously discarded after logging it) so callers can track liveness. Its `CreateProcessAsUser` call no longer passes `CREATE_NEW_CONSOLE` — found via real-hardware testing (visible on a real VNC console): that flag popped up a visible, empty, useless console window alongside the tray, since `beacon-tray.exe` is a pure GUI app with no console I/O.
- **Multi-session support (RDS / AVD / Windows 365)** — added right after Step 2's real-hardware pass, once the user flagged that console-only session targeting doesn't just miss "extra" RDP sessions, it misses these environments *entirely*: RDS has many concurrent sessions with the console typically unused, and AVD/Windows 365 have **no console session at all, ever**, even for a single user — the one session that exists is itself delivered over the RDP protocol. `usersession` gained `RunAsSession(sessionID, exe, args)` (the general form `RunAsActiveUser` now wraps) and `ActiveSessions()` (`WTSEnumerateSessions` filtered to `WTSActive`). `EnsureTrayRunning()`'s state changed from a single last-session/PID pair to a `map[uint32]uint32` (session ID → tray PID) — each call re-enumerates every active session, launches into any without a live tracked PID, and prunes tracked sessions no longer active (the process ends with its session; nothing to explicitly kill, just stop bookkeeping it). The `WTS_SESSION_LOGON` hook needed no changes — it already just calls `EnsureTrayRunning()` with no session-specific argument, which now correctly reconciles every session, not just the one that just logged on. **Not yet re-verified on real hardware** for the multi-session case specifically — Step 2's console-session pass predates this change; `mstsc /admin` gives 2 concurrent sessions on any Windows Server without full RDS licensing as a practical partial test, true RDS/AVD/Windows 365 confirmation needs one of those environments directly.
- **Step 3 — the reboot notification, the original Datto RMM motivation for this whole `usersession`/tray effort**: `install_patches` already computed `wuinstall.Result.RebootRequired` per run but discarded the implication, only reporting it to the worker. Now, when true, the agent writes `agent/internal/rebootmarker.Path()` (`C:\Program Files\Beacon\pending-reboot.json`, Windows real impl, `!windows` stub returning `""`) if one doesn't already exist (never clobbers an in-progress snooze). The path deliberately lives outside `internal/service`: `beacon-tray.exe` imports it, while `service` embeds the built tray; importing `service` from the tray created a recursive build input where every tray build indirectly hashed the previous tray binary and made repeated Windows release builds non-reproducible. No new opt-in toggle for manually-triggered installs — a resulting notification is a direct, wanted consequence of an action a technician just took, not something that needs gating; Patch Policy (built later this session, see below) is what actually needed an opt-in, via its own `auto_reboot` toggle on top of this default. **Polled state, not a named pipe** — deliberately reconsidered from Step 3's original "named pipe is the natural fit" scoping, given how much real Windows-IPC debugging friction this session had already hit; a reboot prompt isn't latency-critical, and a JSON file matches this codebase's existing state-file conventions (`update-state.json`, `credential.json`) instead of introducing connection-lifecycle complexity, especially across multiple simultaneous tray instances on an RDS box. `beacon-tray.exe` polls the marker every 30s; if present and not currently snoozed, shows `windows.MessageBox` (`MB_YESNO|MB_ICONWARNING` — already available in the vendored `golang.org/x/sys/windows`, no new dependency; button meaning is spelled out in the message text since `MessageBox` doesn't support custom button labels the way `TaskDialogIndirect` does, and that API isn't wrapped in the vendored package — not worth a hand-rolled raw syscall for a v1 cosmetic upgrade) in its own goroutine (a bool guard prevents a second prompt stacking on an unanswered one). "Restart Now" writes `confirmed: true` back to the marker — the *agent's* own check-in-loop poll (not the tray) performs the actual `shutdown /r /t 0` (same invocation `worker/src/routes/admin/devices.ts`'s `reboot` command already uses), matching the established "the agent always does the actual privileged action" pattern the rest of patch install already follows, and sidestepping whether a given user's session actually holds `SeShutdownPrivilege`. "Postpone" writes a single fixed 1-hour `snoozed_until` — not Datto's fuller recurring-reminder/deferral-limit model, a deliberate scope-down consistent with this feature's other simplifications. Every active session's tray polls the same file independently, so every logged-in user sees the prompt on a shared machine (a reboot is machine-wide, not per-user); whichever response arrives first governs the whole machine, no per-user state. **Not yet verified on real hardware** — same testing-load reasoning as the still-pending multi-session check.

**Duplicate tray icon on self-update / manual "Restart Agent"** — found via real hardware in a later session, reproduced on two separate machines: `trayPIDs` (`tray_windows.go`) is in-memory-only and always starts empty on a fresh process, but the tray it's tracking is a separate, detached process (`usersession.RunAsSession`) tied to its own session, not a child of the service — it keeps running right through both a self-update binary swap and a `restart_agent`-triggered service restart. The next process's `EnsureTrayRunning()` had no way to know that surviving tray already existed and launched a second one alongside it. Fixed with a `sync.Once`-gated `taskkill /IM beacon-tray.exe /F` at the top of `EnsureTrayRunning()`, run exactly once per process lifetime regardless of which of the three call sites reaches it first — guarantees a clean slate before the normal per-session reconciliation logic (just below it) relaunches exactly one tray per active session and starts tracking it correctly from that point on. A momentary icon blip on every process start, not a lasting duplicate. Same "ignore the error, 'no matching process' isn't real failure" convention as `Uninstall()`'s own `taskkill` call. **Verified on real hardware** (agent v0.2.16, two separate machines updated from a build predating the fix) — no duplicate tray icon after the update.

**Real-hardware verification, and one still-open question.** Tested on a real Vultr VPS's actual console session (via VNC — RDP sessions aren't the console session, confirmed live, a real instance of the exact limitation `usersession` v1 already documented): the core mechanism works — `beacon-agent.exe` installs as a real Windows service, extracts and launches the tray automatically with no manual intervention, correctly targeting the true console session and not the separate RDP session. Two more real bugs found and fixed in the process:
1. **`hardenService`'s SDDL denied `SERVICE_ALL_ACCESS` to everyone, including SYSTEM** (pre-existing code from earlier in this session, unrelated to tray work, but only surfaced now via a real `uninstall` attempt) — SYSTEM's grant was a manually-enumerated rights list that omitted `DE`/`WD`, and once applied, not even `Reharden()` could self-heal it (fixing a DACL needs `WD` too). Fixed by granting SYSTEM `GA` (Generic All) instead of enumerating rights by hand.
2. A stale SDDL from before the fix can still deadlock a real device exactly this way — recovery is registry-level (`Remove-Item HKLM:\SYSTEM\CurrentControlSet\Services\<name>` bypasses the service object's own broken ACL entirely, since registry permissions are separate from it) followed by a reboot (deleting a service's registry key doesn't update the Service Control Manager's in-memory cache until reboot — a known Windows behavior, not Beacon-specific).

**Tamper-resistance hardening (`hardenService`'s SDDL, `hardenInstallDir`'s ACL) was removed in a later session** — it made the agent nearly impossible to work with during further real hardware testing (a hardened service can only be stopped/deleted/reinstalled by SYSTEM, not a local Administrator, forcing exactly the registry-surgery-plus-reboot recovery above on nearly every test cycle). See `agent/internal/service/install_windows.go`'s `setRecoveryActions` doc comment (the function `hardenService` was renamed to, once its SDDL-locking half was stripped out) for the full removal rationale. Worth reimplementing properly at some point, but deliberately pulled out rather than continuing to patch around it live.

**"Zero log activity from a definitely-running process" — root-caused in a later session (PR #55), first fix proven insufficient by the very next real restart (PR #58).** A real production device (Nebuchadnezzar) was found checking in and executing dispatched commands correctly — proven by dispatching a fresh `run_script` command via the admin API and watching it complete successfully — while `agent.log` had been completely silent for two days. Root cause: `setupLogging` (`agent/cmd/agent/main.go`) made exactly one `os.OpenFile` attempt on startup and silently gave up forever on any failure, permanently reverting all logging to `os.Stderr` alone — which a Windows service has no console to display, the exact problem `setupLogging` exists to solve in the first place. One lost race at startup (most likely an AV/EDR scan of the freshly-created/freshly-swapped log file) blacks out logging for the rest of that process's life with zero indication anything went wrong; this also explains the original "killing the tray process didn't trigger a relaunch, and the service log showed no activity at all" observation from the earlier real-hardware test — the relaunch logic may well have been firing correctly the whole time, just invisibly. **First fix (PR #55, agent v0.2.18)** used a bounded retry (5 attempts, 2.5s total) — released, and then directly disproven on the very next real restart of the same device: a confirmed-different PID running v0.2.18 still never wrote a single new line to `agent.log`, while a manual file-open test moments later succeeded immediately (the lock had since cleared) — the real-world contention window outlasts a few hundred ms by a wide margin, apparently especially right after a binary swap/restart. **Second fix (PR #58)**: one synchronous open attempt (zero startup delay in the common case), then on failure a background goroutine retries every 5s *indefinitely* until it succeeds, rather than giving up after a fixed window — `log.SetOutput` is safe to call concurrently with other `log.Printf` calls (the stdlib `Logger`'s own mutex covers it). **Released in agent v0.2.19** (independently re-verified — real download + a from-scratch Ed25519 signature check against the pinned public key, not just trusting `publish-agent.mjs`'s own internal check) — this design can no longer time out the way the first fix did (it either eventually succeeds or never does, a materially rarer/different failure mode), but real-hardware confirmation is still open since the underlying race is inherently hard to force on demand.
- Datto RMM's own tray process (`gui.exe`, confirmed via their docs to run "in every user session") doesn't have its actual launch mechanism publicly documented — checked their agent architecture, restart, and troubleshooting docs directly. The Step 2 design above is an engineering recommendation grounded in what's robust and what was already built and verified, not a confirmed copy of Datto's internals.

**Real-hardware verification of "run as a logged in user" for Jobs (PR #40), a second physical machine (`stcslt001`, separate from the VPS above)**: the core mechanism is confirmed working — `usersession.RunAsSession` genuinely launches a process in a real logged-in console user's session from the SYSTEM-context service (verified via `agent/tools/usersessiontest.exe`, run as a one-shot SYSTEM scheduled task for an instant, network-independent test: `notepad.exe` visibly opened on the physical screen). Two real, distinct findings from this pass:
1. **`beacon-tray.exe` was a console-subsystem binary, not GUI-subsystem** (`scripts/publish-agent.mjs`'s tray build step was missing `-ldflags="-H=windowsgui"`) — every tray launch popped a real, visible, blank console window into the target session (blank because systray never writes to it). Fixed by adding the flag; confirmed via the terminal tab title (`C:\Program Files\Beacon\bea...`, the console's default title when none is set) matching exactly.
2. **Windows client (non-Server) RDP is fundamentally single-session** — connecting via RDP, even `mstsc /admin` (a Remote Desktop *Services*/Server-only feature with no effect on client SKUs), never activates the physical console session; `query session` showed the console session permanently `Conn` with no username the entire time a technician was RDP'd in, explaining several early "no active console session" job failures that looked like bugs but weren't — real physical presence at the keyboard, with the RDP session fully disconnected first, is required to test this feature's success path at all.
3. **Blank-slot tray icon — root-caused in a later session, fixed and released in agent v0.2.19**: after a genuine physical-console login (and again independently, confirmed on Nebuchadnezzar across multiple real reboots), `beacon-tray.exe` launched into the correct session (confirmed via `Get-Process`: correct `SessionId`, live PID) but its icon never rendered in the notification area — not hidden in the overflow flyout either, just a blank reserved slot. Process-level launch targeting was never the issue. Root cause, confirmed against `fyne.io/systray`'s own source and Microsoft's "The Taskbar" docs rather than guessed: this process launches at `WTS_SESSION_LOGON`, which can race explorer.exe's own taskbar/notification-area window creation. `Shell_NotifyIcon(NIM_ADD)` can silently fail to render (while still reserving a slot) if explorer's taskbar window isn't fully up yet, and the systray library's existing `TaskbarCreated`-broadcast handler — Microsoft's own documented fix for exactly this class of app ("services that are already running when the Shell launches") — only helps if this process's message window is already pumping at the single instant explorer broadcasts it; if this process loses that race too, the blank icon is never retried by anything. Fixed (`agent/cmd/beacon-tray/main.go`) with a `periodicIconRefresh()` goroutine — re-issues `systray.SetIcon()` (confirmed from the library's own source to be `NIM_MODIFY`, never `NIM_ADD`, so it can't create a duplicate icon and is safe to call repeatedly) every 30s, indefinitely, matching the existing `pollPendingReboot()` ticker already in this file. Deliberately an indefinite periodic self-heal rather than a one-shot delayed retry with a guessed wait — this codebase has been burned more than once by guessed fixed delays around Windows timing races (see `SelfUninstall`'s `timeout`/`ping` saga above). **Released in agent v0.2.19; a real reboot of Nebuchadnezzar reproduced the blank slot again on the pre-0.2.19 agent, and a subsequent force-update-triggered restart onto v0.2.19 showed the icon rendering correctly** — encouraging, but not yet unambiguous proof of the specific self-heal mechanism: the update swapped the binary and restarted the whole process, so a correctly-rendering icon afterward is consistent with either `periodicIconRefresh()` healing a blank slot on the new process, or simply this particular fresh tray launch not hitting the race at all (the bug was always intermittent, not blank on every single launch). The fully conclusive test — a blank icon appearing on an already-running v0.2.19 tray, left alone, clearing up within ~30s with no further restart/update — hasn't happened yet.
- `agent/internal/audit/hardware.go`'s `collectBIOS{Linux,Windows,Darwin}()` also collect `BIOSInfo.serial_number` now (DMI `/sys/class/dmi/id/product_serial` on Linux — root-only permission, silently empty if the agent isn't running as root; WMI `Win32_BIOS.SerialNumber` on Windows; `system_profiler SPHardwareDataType`'s "Serial Number (system)" line on macOS), and `collectHardware()` also sets `HardwareInfo.last_logged_in_user` via `collectLastLoggedInUser()` (gopsutil `host.Users()` on Linux/Darwin — picks the most-recently-started session; WMI `Win32_ComputerSystem.UserName` on Windows, since gopsutil's `host.Users()` is unimplemented there). Both ride the existing `hardware` audit JSON blob — no new DB column/migration needed for either.
- `HardwareInfo` also carries (v0.2.3/v0.2.4, same "rides the existing JSON blob, no migration" pattern): `Architecture` (free — `runtime.GOARCH`, no collection needed); `System` (`SystemInfo`: Manufacturer/Model/Motherboard — DMI `sys_vendor`/`product_name`/`board_vendor`/`board_name` on Linux, `Win32_ComputerSystem`+`Win32_BaseBoard` on Windows, `system_profiler` "Model Name" on macOS with no motherboard concept there — Macs are unibody); `DisplayAdapters` (`lspci` parse on Linux, `Win32_VideoController` on Windows — wrapped in a `[PSCustomObject]` so `ConvertTo-Json` can't collapse a one-element result to a bare scalar, `system_profiler SPDisplaysDataType` "Chipset Model" on macOS); `RAM.InstalledBytes` (raw physical DIMM capacity, distinct from gopsutil's OS-visible/usable `RAM.TotalBytes` — `dmidecode --type 17` on Linux, same root-only caveat as BIOS serial; `Win32_PhysicalMemory` sum on Windows; `system_profiler` "Memory:" line on macOS); `Domain`/`WindowsDisplayVersion`/`WindowsInstallationType` (Windows-only, no Linux/macOS equivalent — `Domain` only set when `Win32_ComputerSystem.PartOfDomain` is true, since that property returns the *workgroup* name otherwise); `Virtualization` (detected guest platform — `detectVirtualization()` checks `/proc/sys/kernel/osrelease` for WSL2's own kernel signature first, then DMI vendor/product strings for Hyper-V/VMware/VirtualBox/KVM-QEMU/Xen on Linux; `Win32_ComputerSystem` Manufacturer/Model pattern-matching on Windows; `kern.hv_vmm_present` sysctl on macOS — empty string on bare metal or when undetectable. **Not yet in any released agent build**).
- `agent/internal/updater/` (self-update) — `runLoop` checks `/v1/agent/version` every 24h after an initial 5-minute stagger; a successful update writes `<credDir>/update-state.json` and hands off to `awaitConfirmation` on the next process start, which must fall through to `runLoop` again once resolved (a real bug, fixed in v0.2.5) or the device permanently stops checking for updates after one successful cycle. `<credDir>/agent.log` (v0.2.6) is the first thing to check when self-update is ever in question — Windows services have no console, so nothing here was visible in production before this.
- `agent/internal/session/` — handles `open_session` commands (dispatched from `main.go`'s command loop in its own goroutine). `session.go` dials the relay WS and switches on `session_type`; `tunnel.go` is a raw byte pump for `tcp_tunnel` (Secure-RDP-style); `shell.go` (rewritten this session — see "Remote Shell / session system" below) spawns a real persistent PTY-backed shell via `pty_unix.go`/`pty_windows.go`. These two are genuine build-tag-separated files (`//go:build !windows` / `//go:build windows`), not a `runtime.GOOS`-switch single file like `hardware.go` — the Windows ConPTY library needs Windows-only Go packages that don't compile cross-platform, unlike `hardware.go`'s shell-out-to-native-CLI approach.

### Agent release process (`scripts/publish-agent.mjs`)

One self-contained script, run in a single invocation: derives the public half of a host-controlled Ed25519 private key, linker-embeds that key into all 5 platform/arch binaries, creates the selected GitHub release and uploads the binaries, rejects any signing-key/public-key mismatch, re-downloads and cryptographically verifies the public assets, registers them with the Worker, and verifies the unauthenticated Worker version/download path returns the registered metadata and exact hosted bytes. `BEACON_SIGNING_KEY_FILE` (created by `go run ./tools/keygen --out ...`; mode `0600` enforced on POSIX, operator-restricted ACL required on Windows) is preferred; legacy `BEACON_SIGNING_KEY` remains accepted. Also needs `BEACON_WORKER_URL`, `BEACON_ADMIN_SECRET`, an authenticated `gh` CLI, and optionally `BEACON_RELEASE_REPOSITORY=owner/repository` (otherwise safely detected with `gh repo view`). The selected GitHub repository must be public because agents have no GitHub credential. **Run from the repo root.**

```bash
export BEACON_SIGNING_KEY_FILE=/secure/path/beacon-agent-signing.key
export BEACON_WORKER_URL=https://beacon-api.example.com
export BEACON_RELEASE_REPOSITORY=owner/public-beacon-repository
export BEACON_ADMIN_SECRET
node scripts/publish-agent.mjs <version>
unset BEACON_ADMIN_SECRET
```

No separate "create the release first" step and no `BEACON_DOWNLOAD_BASE_URL` env var. The script computes the release URL from the explicit or detected GitHub repository and rejects private repositories. Published version assets are immutable: a same-version retry verifies identical hosted bytes and skips an identical current catalog entry, but never clobbers an existing asset or inserts a duplicate; mismatched/incomplete assets and downgrade attempts fail and require a new version.

`agent/internal/releasekey.PublicKeyHex` owns the upstream default and is replaced with `-X` for a host-controlled release. Both `tools/sign` and `tools/verify` consume that same package-level value; signing fails if the supplied private key's public half differs. The script verifies the direct GitHub asset before registration, then checks both **unauthenticated** Worker endpoints (`GET /v1/agent/version` and `GET /v1/agent/download`) after registration. There is no SHA-only fallback when cryptographic verification cannot run.

Signing-key continuity is an operator contract: existing agents only accept releases signed by the private half of their embedded public key. Losing that private key breaks automatic updates; replacing it requires a planned transition while the old key is still available. The beta workflow does not implement automatic key rotation. Never commit a key file or print private signing material.

## Auth System

Multi-user auth replacing the old single-`ADMIN_SECRET`-only model. Local accounts + Microsoft Entra ID SSO, global RBAC (no per-company scoping — Beacon's users are internal MSP staff, not client-facing).

### Roles
`admin` > `technician` > `readonly` (hierarchy in `worker/src/lib/auth.ts`'s `ROLE_RANK`/`roleAtLeast`). Per-route convention: GET/list → `readonly`; routine mutations (approve device, run job, resolve alert, edit policy) → `technician`; identity, secrets, host-wide configuration, shared dashboards/branding, and fleet agent-release registration → `admin` only. `docs/AUTHORIZATION.md` is the concise route-family matrix and redaction contract.

### `requireUser` (`worker/src/lib/auth.ts`)
Every `/v1/admin/*` and `/v1/sessions` route calls `requireUser(c.req.header('Authorization'), c.env, minRole)` instead of the old `requireAdmin`. It accepts either:
1. `Bearer <ADMIN_SECRET>` — the break-glass token, resolves to a synthetic admin identity, kept working forever (bootstrap + recovery, never surfaced in the dashboard UI), or
2. `Bearer <session token>` — hashed and looked up in `user_sessions` joined to `users`; rejected if revoked, expired, or the user is `disabled`; role checked against `minRole`.

Sessions are opaque random tokens (`generateToken()`/`sha256hex()`, the same convention as `enrollmentTokens.tokenHash`), not JWTs — chosen so logout/disable/role-change take effect on the user's very next request, with no denylist. `user_sessions.last_used_at` is only bumped when stale by more than 5 minutes, to avoid a D1 write on every authenticated request.

### Local auth routes (`worker/src/routes/auth.ts`)
`POST /v1/auth/login` (email+password, generic error either way to avoid enumeration), `POST /v1/auth/logout` (revokes the current session), `GET /v1/auth/me`.

### Microsoft Entra ID SSO (`worker/src/lib/oidc.ts`, `worker/src/routes/auth-microsoft.ts`)
Admin configures one or more Entra security groups mapped to a Beacon role via `/v1/admin/sso/providers` + nested `/group-mappings` (client secret AES-GCM-encrypted at rest using the `CONFIG_ENCRYPTION_KEY` secret — the one place a secret is encrypted rather than hashed, since it must be recovered in plaintext to call Microsoft's token endpoint).

Flow: `GET /v1/auth/microsoft/login` generates PKCE + a `state` row in `sso_login_state` (the row's own id *is* the `state` value — no cookie needed) and redirects to Microsoft requesting `openid profile email GroupMember.Read.All` scope; `GET /v1/auth/microsoft/callback` exchanges the code, verifies the ID token via `jose` (the one deliberate third-party-crypto dependency in the codebase, justified by how easy JWKS/JWT verification is to get wrong by hand), then **always** calls Microsoft Graph `GET /me/transitiveMemberOf` for group membership (not `/me/memberOf` — that only returns direct membership and silently misses nested groups, which are the norm in real Entra tenants; caught during this session's real Entra rollout) — never the ID token's `groups` claim, since Entra only embeds direct-membership claims below ~200 groups and requires a Graph call above that anyway. Zero matching group mappings rejects the login with no user created; multiple matches pick the highest-privilege role (`highestRole()`); role is re-resolved from current group membership on every login. The callback hands the SPA a one-time `sso_exchange_codes` code (not the real token) via redirect, so the session token never appears in a URL; `POST /v1/auth/microsoft/exchange` trades it for the real token.

**Entra app registration requirements** (see README/PROJECT_LOG for the full walkthrough): redirect URI `<worker-url>/v1/auth/microsoft/callback`; API permissions need **two** separate Graph permissions added, both requiring admin consent — `GroupMember.Read.All` as a **Delegated** permission (used at login time, in the scope above) and `Group.Read.All` as an **Application** permission (used by the group-search feature below, via client-credentials — a signed-in admin configuring SSO may not have a Microsoft delegated token available at all).

**Group search** (`GET /v1/admin/sso/providers/:id/groups?search=`, admin-only) — lets the SSO settings page search real Entra groups by display name instead of requiring a pasted Object ID. Uses `getAppOnlyGraphToken()` (OAuth2 client-credentials grant against the provider's own stored client_id/secret) + `searchGroups()` (Graph `/groups?$search=`, requires the `ConsistencyLevel: eventual` header). Falls back to manual Object ID entry in the UI if search fails (e.g. the Application permission isn't granted yet).

Google Workspace is explicitly deferred (v2) but `sso_providers.type` and the group-mapping tables are provider-generic — adding it later reuses the same tables and the same `oidc.ts` verification helper.

**Password hashing runtime limit**: `worker/src/lib/password.ts`'s PBKDF2 iteration count is capped at 100,000, not OWASP's higher recommended floor — Cloudflare Workers' actual edge `crypto.subtle` implementation throws `NotSupportedError` above 100,000 iterations. This did **not** reproduce in local `wrangler dev` testing, only against the real deployed worker — don't trust local dev alone for anything touching `crypto.subtle` limits.

### Dashboard side
`dashboard/src/auth.ts` is a small `reactive` current-user singleton (no Pinia, consistent with the app's existing no-state-library convention) — `loadCurrentUser()` calls `/v1/auth/me`, `hasRole(min)` gates nav items and admin-only routes. `dashboard/src/api.ts`'s `request()` clears the stored token and hard-redirects to `/login` on any 401 outside a login attempt (`skipAuthRedirect` opt-out used by the login/SSO-exchange calls themselves).

**Post-login sidebar data bug (found via real testing)**: `App.vue` (the persistent root shell) fetches its own sidebar data — companies, pending-approval count, dashboards list — once in `onMounted`, guarded by `api.hasToken()`. Since `App.vue` mounts once at initial page load and never remounts across a client-side navigation, that guard is still `false` at the moment of first mount when the user starts on `/login`/`/sso-callback` — so a real login never re-triggers the fetch, and the sidebar's Dashboards section stayed permanently empty (just an empty chevron) until a full page reload reran `onMounted` with a token already present. Fixed by extracting the fetch into `loadAppData()` and calling it a second time in response to a new `beacon:auth-changed` window event, dispatched by `LoginPage.vue`'s `complete()` (both normal and emergency-access login) and `SsoCallbackPage.vue` right after `saveToken`/`saveEmergencyToken` — same event-based refresh convention `beacon:dashboards-changed`/`beacon:pending-changed` already established elsewhere in this file.

**Post-login landing page**: both login paths now `router.push('/')` (→ `DashboardHomePage.vue`'s home-dashboard redirect, see Shared Dashboards below) instead of the previous hardcoded `router.push('/devices')` — a leftover from before Shared Dashboards existed (`/` used to be a fixed `OverviewPage`, deleted when Shared Dashboards shipped) that was never revisited once `/` became a real, user-configurable home dashboard.

### Remote-session WS auth
The pre-existing shell/tunnel session WebSocket (`worker/src/routes/sessions.ts`) used to authenticate its client leg by embedding the raw `ADMIN_SECRET` in the `?auth=` query param — broken once technicians (who never hold `ADMIN_SECRET`) can open sessions too. Each session now gets its own random token at creation time, hashed into `sessions.client_auth_hash`, checked directly (not via `requireUser`, since it's a query param not a header).

### Login page redesign (`dashboard/src/pages/LoginPage.vue`)
Rebuilt as an adaptive, theme-aware flow instead of a static local-only form. On mount, calls `GET /v1/auth/microsoft/available` (`worker/src/routes/auth-microsoft.ts` — true when an Entra provider row exists) and opens directly into the Microsoft button when true, local email/password otherwise; either mode can switch to the other via an explicit link. No new backend surface for the SSO-detection or mode-switching itself — both existing routes (`/v1/auth/microsoft/login`, `POST /v1/auth/login`) are unchanged.

**Emergency administrator access** is a third, visually de-emphasized mode (small "Emergency administrator access" text link, not a prominent button) — reuses `requireUser`'s existing `ADMIN_SECRET` break-glass path with **zero new backend surface**: `verifyEmergencyAccess()` just calls `GET /v1/auth/me` with `Authorization: Bearer <secret>` and checks for a 200. Deliberately kept out of `localStorage` — `api.saveEmergencyToken()` stores it in `sessionStorage` instead (cleared on browser close, never touches the persistent `beacon_token` local-account/SSO session storage), and `saveToken()`/`clearToken()` each clear the other storage's key so the two paths can't both be active at once. This is presentation/storage-only; the underlying authorization behavior (`ADMIN_SECRET` as a synthetic admin identity) is unchanged from the existing `requireUser` contract above.

## Branding (host-configurable color themes)

Host-level (not per-user) color theming — a self-hoster can rebrand Beacon's whole 16-token dark color system without a code change, with built-in presets plus fully custom host-created palettes. Migrations `0033`–`0037`.

### Tables
- `branding_themes` — `id`, `name`, `source` (`'built_in'|'custom'`), `draft_tokens` (JSON, the 16 `ThemeKey`s below), `created_at`/`updated_at`. `source='built_in'` rows are seeded by migration and are **immutable at the API layer** (`PATCH`/`DELETE` 403).
- `branding_theme_revisions` — `id` (`<theme_id>-v<revision>`), `theme_id` FK `ON DELETE CASCADE`, `revision` (int, `UNIQUE(theme_id, revision)`), `tokens` (JSON snapshot), `published_at`. **Custom themes only** — migration `0037` deletes every revision row belonging to a `built_in` theme, since built-ins never had a draft/publish distinction to begin with.
- `branding_settings` — single row (`id=1` `CHECK`), `active_theme_id` FK, `active_revision_id` FK **nullable** (migration `0037` split this out of a single always-required `active_revision_id` — see below).

### Built-in vs. custom activation split (migration `0037`, the key later correction)
`0033` originally gave every theme — built-in or custom — a revision, and `branding_settings` pointed at a revision only. Once more built-ins shipped (`0034`/`0035`), that meant fabricating a synthetic "revision" for something that's already an immutable shipped palette with no real publish/rollback story. `0037` splits activation in two: `activate_theme_id` always set; `active_revision_id` set **only** when the active theme is `source='custom'`, `NULL` for `built_in`. Reflected in the two activation routes below and in `GET /v1/branding/active`'s branching response shape.

### Draft / publish / revision lifecycle (custom themes only)
A custom theme has one **draft** (`draft_tokens`, freely `PATCH`-editable, not yet live for anyone) and up to `MAX_PUBLISHED_REVISIONS = 5` **published revisions** (immutable snapshots, cache-safe URLs). `POST /:id/publish` snapshots the current draft into a new revision, then prunes down to 5 — but **never prunes the currently-active revision**, even if it's aged out of the most-recent-5 window (walks revisions oldest-first, skips the active one, so an old still-live revision survives pruning while a newer unpublished-since draft edit does not). Activating a theme for real (`POST /admin/revisions/:id/activate`) points `branding_settings` at one specific *revision*, not the theme's current draft — this is what makes rollback to an older published revision possible, and what keeps `GET /v1/branding/revisions/:id`'s response safely `immutable`-cacheable (a revision's `tokens` can never change after publish; only the draft can).

### Token set
16 fixed keys (`worker/src/routes/branding.ts`'s `THEME_KEYS`, mirrored client-side in `dashboard/src/theme.ts`): `canvas, surface, surfaceRaised, surfaceBrand, border, borderStrong, textPrimary, textMuted, textSubtle, textOnPrimary, primary, primaryHover, success, warning, danger, info`. Server-side `parseTokens()` requires **all 16** present and each a strict `#rrggbb` hex string (no shorthand, no alpha) — a partial palette is rejected outright, not merged with defaults, so a theme is always a complete, self-consistent set.

`dashboard/src/style.css`'s `:root` tokens are a 1:1 rename to match `THEME_KEYS` (old `--bg`/`--surface`/`--accent`/`--teal`/`--amber`/`--red`/`--text`/`--muted` → `--color-canvas`/`--color-surface`/`--color-primary`/`--color-success`/`--color-warning`/`--color-danger`/`--color-text-primary`/`--color-text-muted` etc., see STYLE.md's Design tokens table) — necessary because live re-theming overwrites these exact custom properties at runtime (`applyTheme()` below).

### Worker (`worker/src/routes/branding.ts`, mounted at `/v1/branding`)
- `GET /active` (public, `no-store`) — the runtime pointer every page load resolves. Built-in active theme: returns `{themeId, name, tokens}` directly (tokens parsed straight from `draft_tokens`, no revision indirection). Custom active theme: returns `{revisionId, themeId, name, revision, publishedAt}` — no tokens inline, forces a second call.
- `GET /revisions/:id` (public, `immutable` cache-control) — fetches a custom theme's actual `tokens` for the pointer above. Never called for built-ins (they return tokens directly from `/active`).
- `GET/POST/PATCH/DELETE /admin/themes[/:id]`, `POST /admin/themes/:id/publish`, `POST /admin/themes/:id/activate` (built-ins only — errors telling you to publish+activate a revision instead for custom), `POST /admin/revisions/:id/activate` (custom only) — all **admin-only** (`requireUser(..., 'admin')`), matching the Settings-area role tier (SSO, Custom Field definitions, Users).
- Delete guard: a theme can't be deleted while active (`409`) — must activate a different theme first, same shape as other "can't delete what's in use" guards elsewhere in the codebase.

### Dashboard (`dashboard/src/theme.ts`, `dashboard/src/pages/BrandingSettingsPage.vue`)
- `loadActiveTheme()` runs once, **before** `createApp(App).mount()` in `main.ts` — applies a hardcoded `defaultTheme` constant synchronously first (so the app is never unstyled/flashing), then fetches `/v1/branding/active` (+ `/revisions/:id` if needed) with a 2.5s `AbortController` timeout, swallowing any failure silently. **Login must never be held hostage by branding** — a slow or down branding endpoint degrades to the shipped default palette, never a blocked login screen.
- `BrandingSettingsPage.vue` (`/settings/branding`, admin-only) — theme picker + live draft editor. Selecting a theme immediately calls `applyTheme()` on the *whole app* as a preview (a `watch(draft, ..., { flush: 'sync' })`, not just a preview pane) — actually repaints the running dashboard so an admin sees the real effect, not a swatch. "Save Draft" persists `draft_tokens` without publishing; "Publish" snapshots + prunes as above; only an explicit Activate call changes what other users see.
- Inline WCAG contrast warnings (not a hard block) — computed contrast ratio between `textPrimary`/`canvas` and `textOnPrimary`/`primary`, flagged below 4.5:1 (AA body-text threshold). Advisory only; an admin can still save/publish/activate a theme that fails the check.

### Seeded built-ins
Default (refined in `0036` — v2 replaces v1 as the shipped baseline, but `0036` deliberately does **not** reassign a host's already-active *custom* theme, only advances hosts still sitting on `default-v1`), Sentry-i, Cobalt2-i, SyntaxFM-i, Slate — all complete, immutable 16-token palettes, explicitly labeled as inspired-by / adapted-from rather than implying endorsement by the referenced projects (see each migration's own SQL comment).

### Identity (product name + logo)
Scoped against a Datto RMM Branding reference (User Interface/Agent/Support Request tabs) — most of it doesn't apply: Header Background Color is already covered by `surfaceBrand` above, Report Logo has no reporting feature to attach to, and the entire Agent tab (tray icons, reboot-prompt text, OnDemand mode) and Support Request tab assume a desktop-GUI agent and end-user support-ticket system that don't exist in Beacon (the Go agent is headless). Only Product Name and a logo mark are real, buildable gaps — see PROJECT_LOG.md for the full scoping writeup. Built across two passes (backend, then dashboard UI) — the migration's number shifted from its original `0038` to `0045` between the two, since this project now merges everything through PRs and a release-automation step renumbers migrations by merge order (see "Database" above).

- `branding_identity` — a second singleton table (`id=1 CHECK`), deliberately **separate from `branding_settings`** rather than new columns on it — that table is strictly the theme-activation pointer, this is a different concern (name + logo) with its own lifecycle. Columns: `product_name` (`''` = unset, falls back to "Beacon" client-side), `logo_key` (nullable R2 object key), `updated_at`. No `logo_content_type` column — `R2ObjectBody.writeHttpMetadata()` reconstructs it from what was stored at `put` time, so a D1 copy would be pure redundancy.
- **First file-upload feature anywhere in this codebase** — new `LOGOS` R2 bucket binding (`bucket_name = "beacon-logos"`, added to `Bindings` in `index.ts` and `[[r2_buckets]]` in both `wrangler.toml`/`.example`). `wrangler dev` auto-emulates R2 locally via Miniflare once the binding is present — no real bucket needed for local dev, only for `wrangler deploy`/`--remote` migrations.
- `POST /v1/branding/admin/logo` (admin) takes a **raw binary body**, not multipart — `Content-Type` header carries the mime type (allow-list: `image/jpeg|png|gif|svg+xml`), size capped at 1MB (fast-path reject via `Content-Length` header when present, authoritative check after buffering since a stream can lie about/omit its length). Generates a fresh `crypto.randomUUID()` key per upload, writes to R2, updates `branding_identity.logo_key`, **then** deletes the previous R2 object if one existed — put-then-commit-then-delete-old ordering so a mid-failure never leaves zero valid logos.
- `GET /v1/branding/logo/:key` (public, `immutable` cache — key is unique per upload, safe to cache forever) streams the R2 object straight through (`c.body(obj.body, 200, ...)` with `writeHttpMetadata()`-derived headers). `GET /v1/branding/identity` (public, `no-store`) is the tiny pointer, same shape as `/active` above.
- CORS needed no changes — `/v1/branding/*` was already covered and `allowHeaders` already includes `Content-Type` generically (not restricted to `application/json`), so the raw-binary POST's preflight passes as-is.
- `dashboard/src/brand.ts` — a `reactive` singleton + loader, mirroring `auth.ts`'s shape (not `theme.ts`'s stateless-DOM-mutation shape) since `App.vue`'s sidebar mark/name and `LoginPage.vue`'s brand lockup both need real template bindings (`:src`, `{{ }}`), not just CSS custom properties. `loadBrandIdentity()` reuses `loadActiveTheme()`'s pre-mount/2.5s-timeout/swallow-failure pattern and runs in parallel with it in `main.ts`. **Always sets both `productName` and `logoUrl` unconditionally on a successful response** (falling back to the defaults when unset), not just when truthy — a real bug caught by Playwright testing: `BrandingSettingsPage.vue` calls this same loader again after an admin *clears* a value (Remove Logo, blank Product Name), and an early version that only wrote truthy values left the sidebar/login stuck on the last-set logo forever after removal, since nothing ever told it to revert.
- Only a single **Product Name** field exists (no separate Company Name) — confirmed with the user that Beacon has exactly one real UI surface to drive today (sidebar/login/tab title), and a second field with no effect would be the same "fake toggle" problem already avoided elsewhere in this codebase.
- `BrandingSettingsPage.vue`'s new Identity section (placed before Themes) calls `loadBrandIdentity()` after every save/upload/remove — the sidebar and login page repaint live, the same "actually see the real effect" convention the theme picker's `applyTheme()` preview already established.
- **Two static default-logo assets, not one** (`dashboard/public/`): `favicon.svg` is the real Beacon mark (an angular purple flame) as a **full, self-contained app icon** — its own baked-in rounded-square background + radial glow, used unmodified as the actual browser-tab favicon (`index.html`'s `<link rel="icon">`), which has no surrounding themed box. `brand-mark.svg` is a **transparent-background crop** of just the flame (tighter viewBox, no background rect/glow defs) — this is `brand.ts`'s default `logoUrl` fallback (used whenever `branding_identity.logo_key` is unset) and `SsoCallbackPage.vue`'s hardcoded mark, since `.sidebar-brand-mark`/`.lp-mark`/`.sc-mark` all draw their **own** background box already themed via `--color-surface-brand`. Dropping the full favicon asset into those spots would nest one rounded square inside another with a fixed (non-themed) color, defeating the whole point of a host-configurable color theme for that one element. If this default logo is ever replaced again, regenerate **both** files (crop a new transparent mark from whatever full asset is provided) rather than pointing every spot at one file.

## Shared Dashboards

Replaced the old fixed `OverviewPage` with host-wide, admin-configurable dashboards (migration `0039`). `OverviewPage.vue` was deleted (it had already become dead code — no longer imported by `main.ts` or linked from `App.vue`, only referenced by two stale comments, which were also fixed).

### Tables
- `dashboards` — `id`, `name`, `sort_order`, `is_home` (bool, exactly one row at a time — enforced procedurally, not a DB constraint: `PATCH .../:id {isHome:true}` first clears every other row's flag in the same batch), timestamps.
- `dashboard_companies` — `(dashboard_id, company_id)` composite PK, `ON DELETE CASCADE`. Zero rows for a dashboard means unscoped (shows all companies) — same "empty = unrestricted" convention as Policy Targeting.
- `dashboard_widgets` — `id`, `dashboard_id`, `type` (one of a fixed `WIDGET_TYPES` set — same bare-`TEXT`-no-migration-needed convention as `policy_monitors.check_type`), `title` (nullable override), `config` (JSON, currently unused by any V1 widget type), `grid_x/y/w/h` (12-column grid, `validLayout()` enforces `1<=w<=12`, `x+w<=12`), `sort_order`.

### Templates vs. real dashboards
`TEMPLATES` (`worker/src/routes/admin/dashboards.ts`) is an **in-code constant**, not a DB row — `blank` (zero widgets) and `default` (8 pre-arranged widgets) are just starting layouts copied into a brand-new `dashboards` row on `POST /`; there's no "template" table or foreign key, a created dashboard is a fully independent, freely-editable copy from the moment it exists. At least one dashboard must always exist (`DELETE` 409s if it's the last one); deleting the current home dashboard promotes the next one by `sort_order`.

### Routing and home-dashboard redirect
`/` → `DashboardHomePage.vue` (a thin redirect shim: fetches the dashboard list, finds the `isHome` one — or falls back to the first — and `router.replace`s to `/dashboards/:id`; a fetch failure is swallowed since `DashboardPage.vue` will surface the same error itself post-navigation). The real content lives at `/dashboards/:id` (`DashboardPage.vue`).

### Data fetching
`GET /v1/admin/dashboards/:id/data` calls `buildDashboardData()` (`worker/src/lib/dashboardData.ts`) once per dashboard, scoped to `dashboard_companies` (or an explicit `?company_id=` override — deliberately wins over the saved scope, matching how the rest of the app's `?company=` query-driven navigation already overrides saved context elsewhere) — **one batched query for every widget on the page**, not a request-per-widget fan-out. Dashboard data refreshes client-side every 30 seconds.

### Widget library (V1, real data only)
`device_summary`, `online_offline`, `os_distribution`, `class_distribution`, `antivirus_status`, `offline_by_type`, `alerts_by_priority`, `recent_alerts`, `patches_by_severity` — every one backed by data Beacon already collects. **Explicitly out of scope**: M365 widgets (no underlying integration, same reasoning as Summary section's excluded fields elsewhere in this doc); iframe/arbitrary-query/presentation/cycling widgets (no embedding or ad-hoc query surface by design — RBAC and data stay inside Beacon, not delegated to something like Grafana).

**`patches_by_severity`** (added once Patch Management existed to back it) — a donut of distinct pending Windows Updates by severity (`DashboardSummary.by_patch_severity`, computed in `buildDashboardData`), same shape as `alerts_by_priority`. Deliberately a lighter-weight scan than `GET /v1/admin/patches`' own — dedupes by `update_id` across the dashboard's company scope and counts by severity, but doesn't merge in fleet-wide approval status (`patch_approvals`) — a widget is meant to answer "how much needs attention at a glance," the full approve/ignore decision workflow stays the dedicated Patches page's job. Not added to the seeded `default` template layout; available via "+ Add widget" like any other type.

### Grid engine: gridstack.js (replaced a hand-rolled CSS Grid + native-HTML5-drag system)

The original implementation (plain CSS Grid, `grid-column`/`grid-row` inline styles, native HTML5 drag-and-drop that swapped two widgets' positions on drop, `−`/`+` buttons that only ever resized width one column at a time) had no collision detection or compaction anywhere, and height was never resizable at all despite `grid_h` already existing in the schema and already being fully server-validated (`1<=h<=12`, same as `w`) — a pure frontend gap, not a backend one. Asked to fix a bottom-right resize handle, then explicitly asked to research real dashboard products' patterns rather than patch the hand-rolled system further (confirmed via research, not assumed) — **gridstack.js** is the answer: framework-agnostic, ships an official first-party Vue 3 wrapper (`gridstack/dist/vue`, distinct from the smaller/less battle-tested Vue-native alternatives), handles drag/resize/collision/auto-compaction/min-max constraints natively instead of Beacon reinventing that math by hand. Beacon's first drag-grid-layout dependency, same "first X dependency in this codebase" honesty this doc already gives `@xterm/xterm`/`fyne.io/systray`.

**Zero backend changes** — `dashboard_widgets` (`grid_x/y/w/h`, migration `0039`) already models exactly a 12-column grid with independent w/h per widget, and `PATCH .../widgets/:id {layout:{x,y,w,h}}` already accepted full layout updates. This was entirely a frontend rendering/interaction rewrite.

- **Split into two components**: `DashboardPage.vue` now only owns grid mechanics (data loading/polling, the `<GridStack>` element, add/remove-widget plumbing, the picker/settings modals) — all per-widget *content* rendering (the three shapes: `device_summary` stat grid, `recent_alerts` table, generic `DonutChart` for everything else) and their helper computeds (`chartData`, `chartCenter`, `activeAlerts`, `alertMessage`, etc.) moved to a new `dashboard/src/components/DashWidget.vue`, since gridstack-vue's `<GridStack :components="{...}">` maps widget-type strings to real Vue components it instantiates itself.
- **`options.children` IS re-read on every `updateOptions()` call, via `if (o.children?.length) this.load(o.children)`** — an earlier version of this doc claimed the opposite (that `children` is read once at init and never re-synced); that was a real misreading of the gridstack source, not a deliberate design choice, and it caused a real bug: `gridOptions`'s computed always includes `children` (derived from `dashboard.value.widgets`), so *any* options change (including the Edit layout/Done editing toggle, which only intends to flip `staticGrid`) also triggers `grid.load(children)`, reconciling every widget's position against whatever is currently in `dashboard.value.widgets`. Since `onGridChange` originally only persisted a drag/resize to the *server* and never updated that local array, the very next options recompute (e.g. clicking Done editing right after a drag) silently snapped every dragged widget back to its stale pre-drag position — masked because the 30s poll's next `load()` would eventually refresh `dashboard.value` with correct server data and "fix" it, making the bug look like a ~30s-delayed visual glitch rather than what it was. Fixed by keeping `dashboard.value.widgets` in sync on every mutation, not just creates: `onGridChange` updates the matching entry's `x/y/w/h` locally in addition to the `PATCH` call, and `DashWidget.vue`'s remove path calls a `provide`d `dashboardRemoveLocalWidget(id)` callback (splicing the array) in addition to its own imperative `grid.removeWidget()` — both now use the exact same local-state discipline `addWidget()` already had (`dashboard.value.widgets.push(created)` before the imperative `grid.addWidget()` call). `staticGrid: !editing` still needs no special-case code of its own; it was never the actual bug.
- **`:key="dashboard.id"` on `<GridStack>`** forces a full unmount/remount when switching dashboards (since `children` is otherwise never re-read) — the one place a full teardown is actually wanted, since switching dashboards is a big enough change to warrant it anyway.
- **Shared, independently-changing state (`data`, `editing`) is `provide`/`inject`ed**, not passed as gridstack node `props` — node props only flow through gridstack's own add/update lifecycle (`gsUpdateVueComponents`), not on every Vue reactivity tick, and `data` refreshes on its own 30s timer completely independently of any widget layout change. `provide`/`inject` works across gridstack-vue's `<Teleport>`-based rendering (Vue's provide/inject follows the *component* tree, not the DOM tree, so the teleport doesn't break it) — confirmed by reading the wrapper's own source, not assumed.
- **A real gap in gridstack's shipped `.d.ts`**: `expose({ getGrid })` (confirmed present at runtime by reading `dist/vue/gridstack.js`) isn't reflected in the type declarations at all, and the Vue wrapper's extended `GridStackWidget` (`component`/`props` fields) isn't accepted by the core `GridStack` class's own stricter TS-declared `addWidget()` parameter type even though the runtime handles it identically either way. Both worked around with narrow, explained casts at the exact call sites (`DashboardPage.vue`'s `rawGrid()` helper and `addWidget()`), not a blanket `any`.
- Gridstack's default drag-placeholder (`rgba(0,0,0,.1)`) is nearly invisible against this app's already-dark theme — overridden via `:deep()` to the same dashed-primary-color language `.add-widget` already uses elsewhere on this page.
- **Verified end-to-end via Playwright, driven directly rather than asking the user to manually test** — no MCP browser tool was connected this session, so `playwright` was installed standalone (npm, into a scratch directory, not added to the project's own dependencies) and scripted against the real local `wrangler dev`/`pnpm dev` servers: emergency-access login, drag-reorder, resize via the corner handle, add/remove widget, and a real page reload to confirm persistence actually round-tripped through D1, not just client state. Found and fixed two real bugs this surfaced, neither catchable by type-checking or a build:
  1. **A resize past `h=12` silently reverted.** The drag itself worked (gridstack's live `gs-h` attribute correctly tracked the drag), but `PATCH .../widgets/:id` came back `400` and the widget snapped back on mouseup. Root cause: `validLayout()` (`worker/src/routes/admin/dashboards.ts`) still capped `h` at `12`, a stale limit that even the seeded `default` template's own `recent_alerts` widget (`h:14`) already exceeded — template inserts just never went through that validation before, so nothing had ever exercised the mismatch until a real resize drag did. Raised the cap to `24` to match the dashboard's own `maxH` widget constraint.
  2. **Every donut-chart widget rendered its title overlapping the chart itself**, confirmed via live computed-style inspection (`.grid-stack-item-content` measuring `36px` tall against a title alone needing `~20px` plus a real chart). Root cause: `cellHeight: 8` was ported directly from the old CSS Grid system's `grid-auto-rows: 8px` without accounting for *why* that system's widgets were actually much taller than `h × 8px` — CSS Grid's `row-gap` is included *inside* a spanned item's own height, which gridstack's `h × cellHeight` model has no equivalent of. Fixed by raising `cellHeight` to `20`, fit to land close to the old system's real pixel heights across its existing `h` values (7, 8, 14) rather than guessed.
- **Still not decided, a real product-feel call**: `float: false` (auto-compaction on, the current default) vs `float: true` (allow gaps) — verified functional either way, just not compared side-by-side live yet. Mobile/narrow-viewport behavior isn't wired up (the old system had a `@media (max-width:760px)` stacked-block fallback; gridstack supports responsive `columnOpts` for the same effect). The default resize handle's grey SVG icon wasn't restyled for the dark theme, though it read clearly enough in testing to not be an immediate problem.

## Two-Tier Policy / Monitor System

The alert/monitoring system uses a **policy → monitor** hierarchy. The old flat `alert_definitions` table is gone.

### Tables
- `policies` — named policy with scope (`global` or `company`), OS/class targeting (JSON arrays), enabled flag
- `policy_monitors` — individual check rules attached to a policy: check_type, config (JSON, shape varies by check_type), alert_priority, sustained_minutes, check_interval_minutes, auto_resolve, auto_resolve_after_minutes, notify_webhook, notify_email (migration 0047 — per-monitor opt-in for external notifications, see Alert Notifications below; default false, independent of the alert itself firing)
- `alert_state` — per (device, policy_monitor) pair: condition_first_seen, is_alerting, alerted_at, resolved_at

`check_type` is a bare `TEXT` column with no SQL `CHECK` constraint — adding a new check type is a TS-enum-only change (`schema.ts`, `routes/admin/policies.ts` `VALID_CHECK_TYPES`, `dashboard/src/api.ts`) with **no migration required**.

### Check types

Ten check types across four evaluation shapes:

**A. Sampled every check-in (60s), evaluated directly against `Metrics`:**

| Type | Config | Notes |
|---|---|---|
| `disk_space` | `{drive, threshold_type, threshold_value, min_disk_gb}` | `drive: "any"` or a specific device/label match; `threshold_type: gb_free\|gb_used\|percent_used` |
| `cpu_usage` | `{percent_max}` | `>=` comparison ("has reached") |
| `memory_usage` | `{percent_max}` | `>=` comparison |
| `av_status` | `{av_state}` | key `av_status:${av_state}` allows 3 sub-monitors (not_detected/not_running/running_not_up_to_date) per policy |

**B. Cron-evaluated (every 2 min), not tied to check-in:**

| Type | Config | Notes |
|---|---|---|
| `offline` | `{direction: 'offline'\|'online', offline_after_seconds}` | `direction: 'offline'` (default) = alert when silent past threshold; `direction: 'online'` = alert once device has been checking in continuously for `sustained_minutes` (presence grace: 5 min) |

**C. Agent-measured — "assign → measure → report" pattern** (see below): worker tells the agent what to check in the check-in *response*, agent measures async, reports back on the *next* check-in via a `pending_*_results` field:

| Type | Config | Assigned via | Reported via |
|---|---|---|---|
| `file_size` | `{path, mode: below\|over, threshold_mb}` | `file_size_checks` | `pending_file_size_results` |
| `ping` | `{target, packet_count, check_unreachable, packet_loss_pct, latency_ms}` — bundles all 3 Datto conditions into one monitor/one alert | `ping_checks` | `pending_ping_results` |
| `process` | `{process_name, mode: running\|stopped\|cpu\|memory, threshold_pct}` | `process_checks` | `pending_process_results` |
| `service` | `{service_name, mode, threshold_pct, boot_delay_minutes}` — Windows only; `boot_delay_minutes` gates *assignment* (not evaluation) using `metrics.uptime_seconds`, so services still starting after boot don't false-alert | `service_checks` | `pending_service_results` |

**D. Audit-evaluated (not check-in) — event-driven, not state-driven:**

| Type | Config | Notes |
|---|---|---|
| `software` | `{name_pattern, mode: installed\|uninstalled\|version_changed}` | Evaluated from `worker/src/routes/audit.ts`'s existing `diffSoftware()` output on every `POST /v1/audit`, not check-in. `%`-wildcard name matching. **Never auto-resolves** (hardcoded `auto_resolve: false`, hidden in UI) — Datto's own spec requires manual resolution. `sustained_minutes` is always `0` (fire on first detection; see fire-immediately fix below) |

### "Assign → measure → report" pattern (agent-executed checks)

Used by `file_size`/`ping`/`process`/`service`. Mirrors the pre-existing `commands`/`pending_command_results` shape:
1. `evaluateCheckinAlerts` (in `worker/src/lib/alerts.ts`) resolves effective monitors for the device, and for these four types pushes an assignment (`{monitor_id, ...}`) into the check-in *response* instead of evaluating anything — returns a `CheckinAssignments` object (`{fileSizeChecks, pingChecks, processChecks, serviceChecks}`).
2. Agent (`agent/cmd/agent/main.go`) receives the response, dispatches one goroutine per assignment (`agent/internal/{filesize,pingutil,procutil,svcutil}`), buffers results in a `pendingMu`-guarded package var, and sends them on the *next* check-in.
3. Worker evaluates each category with its own `evaluate*Alerts` function (`evaluateFileSizeAlerts`, `evaluatePingAlerts`, `evaluateProcessAlerts`, `evaluateServiceAlerts`), all calling the shared `processAlertState`.
4. `check_interval_minutes` throttles *assignment* (not just evaluation) — a monitor is only assigned on check-ins where `Math.floor(now/60) % checkIntervalMinutes === 0`, stateless (no "last checked" storage needed).

Agent packages added this session (all follow the shell-out-to-native-tool or gopsutil convention already used by AV/BIOS collection): `diskutil` (multi-drive enumeration, shared with the audit collector), `filesize` (stat/walk), `pingutil` (shells to native `ping`, parses output), `procutil` (gopsutil `process` package), `svcutil` (Windows-only, `Get-CimInstance Win32_Service` → PID → gopsutil).

### Scope resolution
`resolveEffectiveMonitors` groups matched monitors **by check_type**, not per-monitor: if any company-scoped policy has monitors of a given check_type for the device, its monitors *entirely replace* the global ones for that type — never merged monitor-by-monitor. This is what lets multiple monitors of the same check_type coexist on one policy (av_status's 3 states, cpu_usage's critical+warning pair, multiple ping targets, etc.) without a company override accidentally leaving a stray global monitor active alongside it.

### Two bugs found and fixed this session (both in `processAlertState`, `worker/src/lib/alerts.ts`)
1. **Dedup collision**: the old scope-resolution key was `checkType` alone (`av_status` special-cased) — two monitors of the same check_type (e.g. two `cpu_usage` thresholds) silently collapsed to one. Fixed by the group-based resolution above.
2. **Fire-immediately**: the first-ever observed `failed=true` for a (device, monitor) pair only ever seeded `condition_first_seen` — it required a *second* consecutive failure to actually set `is_alerting=1`. Invisible for 60s-polled monitors (a confirming sample arrives a minute later) but fatal for one-shot/event-driven checks (`software`) where a transition is only ever observed once. Fixed: when `sustained_minutes === 0`, fire on first detection.

### Default global policies (seeded)
- **Antivirus Health** — 3 monitors: not_detected (critical/5m), not_running (high/10m), running_not_up_to_date (moderate/60m)
- **Disk Space** — 1 monitor: any drive < 10 GB free (high/5m, auto-resolves in 120m)
- **Device Offline** — 1 monitor: offline after 30 min (high, auto-resolves in 30m)
- **Memory Usage** — 1 monitor: ≥ 90% (high/10m, auto-resolves in 30m)
- **CPU Usage** — 2 monitors: ≥ 100% (critical/5m) + ≥ 95% early warning (high/15m) — per Datto's own recommended two-tier pattern
- `file_size`/`ping`/`process`/`service`/`software` have no seeded defaults — no universal target/name/path/process is sane to bake in; operators create their own.

## Alert Notifications

Global (hoster-level), not per-company — Beacon is used by an MSP to monitor their clients, and it's the MSP's own team that reads alerts, not the client company being monitored. Client-facing notification, if ever needed, is out of scope here (would run through a separate PSA integration). Two independent channels, both potentially fired from the same 3 sites inside `processAlertState` (`worker/src/lib/alerts.ts`) — the two `alert.triggered` sites and the one `alert.resolved` (auto-resolve) site — never from `reconcileOrphanedAlerts`/`resolveAllOpenAlerts` (admin bulk-resolve paths, not real-world condition changes).

### Per-monitor opt-in (migration 0047) — researched against Datto RMM's real notification model
The alert itself always fires and is always visible in Global Alerts, regardless of notification config — that part is unconditional (`alert_state` gets written either way). Whether it *also* reaches webhook/email is a separate, per-monitor decision: `policy_monitors.notify_webhook`/`notify_email` (both boolean, default `false` — including for existing/seeded monitors, since notifications should only go out when explicitly enabled, not retroactively) gate the `fireWebhooks`/`sendAlertEmails` calls independently at all 3 companies in `processAlertState`. This mirrors Datto RMM's actual model, confirmed against their docs rather than assumed: an alert firing and a monitor's "Send an email" response are two separate toggles, and recipients are configured once, globally (Datto's "default recipients," Beacon's Notification Settings page) rather than per-monitor — only the on/off switch is per-monitor, not the recipient list itself. Beacon splits this into two independent toggles (webhook + email) rather than Datto's one (email + a separate PSA-ticket toggle), since Beacon has two real channels. Datto's further per-monitor "Additional Recipients" (one-off addresses bypassing the global list) was considered and iceboxed — see Icebox below.

Surfaced in `PolicyFormPage.vue`'s Add/Edit Monitor drawer as a "Response" section with two drawer-style toggles ("Send a Webhook" / "Send an Email"). This section pre-existed as a `sendWebhook` stub before migration 0047 — it rendered and toggled visually but was never sent in any `monitors.create`/`update` API call and was hardcoded back to `false` on every page load, a real dead-UI bug fixed as part of wiring this up for real.

### Webhooks
`webhook_endpoints` (`id`, `url`, `enabled`, `created_at`) predates this feature by many sessions (migration `0002`) but was never wired to any dashboard UI, and was originally per-company (`company_id` FK) — migration `0046` rebuilt the table to drop that column once the global model was confirmed. `fireWebhooks()` POSTs `{event, timestamp, device_id, company_id, hostname, check_type, monitor_id, policy_id, config}` to every `enabled=1` row via `Promise.allSettled` (fire-and-forget, no retry). **Deliberately unsigned** — the user's own call: "we just need to send out webhooks, we don't need to ingest them, the hoster can put in their own endpoint at like Hookdeck" — a receiver that needs authenticity verification fronts the URL with something like Hookdeck itself rather than Beacon implementing HMAC signing.

### Email — real plugin architecture
`worker/src/lib/email/` — explicitly requested as an adapter/plugin design, not a flat if/else, so a future provider is one new file, not a change to shared code:
```
worker/src/lib/email/
  types.ts        — EmailProvider interface ({send(config, message)}) + EmailMessage type
  providers/
    resend.ts      — POST api.resend.com/emails, Bearer auth, JSON body
    mailgun.ts      — POST api.{mailgun.net|eu.mailgun.net}/v3/<domain>/messages, HTTP Basic, form-encoded body
    ses.ts          — POST email.<region>.amazonaws.com/v2/email/outbound-emails, hand-rolled AWS SigV4 (no SDK — too large for Workers), JSON body
  registry.ts      — Record<ProviderType, EmailProvider> — the one place that knows every provider exists
  index.ts         — sendEmail(env, to[], subject, html, text): the only export alerts.ts imports, zero provider-specific branching
```
Every provider file owns its own auth scheme and request encoding entirely — confirmed correct against each provider's real API during this session's verification pass (Resend/Mailgun/SES all rejected fake credentials with a real, well-formed API error — `401`/`403`/`SignatureDoesNotMatch`-class responses, not a parse error — proving the request shape itself, not just that *something* was sent).

**SES's SigV4 signer** (`providers/ses.ts`) is the one genuinely fragile piece — a hand-rolled canonical-request → string-to-sign → HMAC-SHA256 signing-key-chain (`"AWS4"+secret → dateStamp → region → "ses" → "aws4_request"`) implementation, entirely via `crypto.subtle`. A wrong-but-parseable signature and a correct one look identical against a fake key (both get rejected) — only a real AWS key proves the signing math is actually right, not just well-formed. Verify with a real key before trusting a production SES release.

**Config storage**: singleton `email_settings` table (`id=1 CHECK`, mirrors `branding_identity`'s shape) — one active provider at a time, not a list. `config_ciphertext`/`config_nonce` hold the *entire* provider-specific credential blob as one AES-GCM string (shape varies by provider, so per-field encryption doesn't fit) via the same `encryptSecret`/`decryptSecret` + `CONFIG_ENCRYPTION_KEY` pattern `sso_providers` already established — same "secret never returned, blank input means keep existing" contract. `worker/src/routes/admin/email-settings.ts` runtime-validates `provider` against the 3 known values on `PATCH` — the TS type annotation on the request body only checks TypeScript callers, not the actual JSON payload; an unvalidated bad value would otherwise sit silently in the column until `sendEmail()` threw on `PROVIDERS[undefined].send()` (a real gap caught during this session's own verification pass, fixed before merge).

### Recipients — two unioned sources
- `users.receives_alerts` (bool, default false) — opt-in per existing Beacon account, reuses `users.email`.
- `notification_emails` (new table: `id`, `email`, `enabled`, `created_at`) — standalone addresses with no Beacon account (a shared mailbox, a ticketing system's inbound address, etc.).
- `sendAlertEmails()` unions both (`SELECT ... WHERE receives_alerts=1 AND status='active'` plus `SELECT ... FROM notification_emails WHERE enabled=1`, deduped via `Set`) — no-ops on zero recipients, same shape as `fireWebhooks`'s empty-list early return. Email links back to the alert via `${env.ALLOWED_ORIGIN}/#/global/alerts/<alertStateId>`.

### `env` threading through `alerts.ts`
`processAlertState` and the 7 `evaluate*` functions (`evaluateCheckinAlerts`/`evaluateFileSizeAlerts`/`evaluatePingAlerts`/`evaluateProcessAlerts`/`evaluateServiceAlerts`/`evaluateSoftwareAlerts`/`evaluateOfflineAlerts`) all gained an `env: Bindings` parameter so `sendAlertEmails` (which needs `CONFIG_ENCRYPTION_KEY` and `ALLOWED_ORIGIN`, neither available from just a D1 handle) can be called alongside the existing `fireWebhooks`. Threaded from `checkin.ts` (5 sites), `audit.ts` (1 site), and `index.ts`'s `scheduled()` handler (1 site) — all already had `env`/`c.env` in scope, previously passed only `.DB`.

### Dashboard
`NotificationSettingsPage.vue` (`/settings/notifications`, admin-only) — one page, three sections (Webhooks list, Email Provider config, Recipients), reusing `SsoSettingsPage.vue`'s `.pf-*`/`.seg-bar`/`.pf-monitors`/`.pf-mon-row` CSS verbatim (duplicated per this codebase's convention, not shared). The provider config form only sends `config` in the `PATCH` when at least one credential field for the selected provider is non-empty — partial credential updates aren't supported, matching the "whole blob, not per-field" storage design; the UI says so directly rather than attempting field-level merge semantics.

## Components / Job System

Script/application library (`components`) + delivery mechanism (`jobs` → `commands`), extended this session toward Datto RMM's Component Library parity (deliberately not 1:1 — see "explicitly out of scope" below).

### Tables
- `components` — `type` (`script`|`application`, drives behavior: Applications currently execute identically to Scripts, no file-attachment support yet — label-only, groundwork for a later pass once object storage exists), `origin` (`custom`|`store` — ComStore provenance), `scope` (`global`|`company` — **`company` means restricted to the companies listed in `component_companies` below, a real many-to-many list, not a single company**; `company_id` is a vestigial, unused column left over from a superseded single-company design, see below), `category` (freeform organizational tag, shown in the UI as "Group" — deliberately renamed so it isn't confused with `type`), `shell`/`script`/`timeout_seconds`, `post_conditions` (JSON array, see below), **`target_os`** (`null`|`'windows'`|`'linux'`|`'darwin'` — filters at dispatch time in `insertJobCommands`, not at creation time; store-origin components have the Platform field disabled in `ComponentFormPage.vue`; `isStore` ref set on load from `comp.origin === 'store'`).
- `component_variables` — typed input variables per component: `name` (env-var identifier, validated against `^[A-Za-z_][A-Za-z0-9_]*$`), `label`, `type` (`string`|`selection`|`boolean`|`date`), `options` (JSON `{label,value}[]`, only for `selection`), `default_value` (always a string regardless of declared type — Datto's own convention, replicated), `description`, `required`, `sort_order`.
- `component_companies` — many-to-many `(component_id, company_id)` membership for `scope='company'` components, `UNIQUE(component_id, company_id)`, `ON DELETE CASCADE` both directions. Added in migration `0022` to replace `0021`'s single-`company_id` design once real Datto reference screenshots showed an "Add Company" flyout that adds companies one at a time to a list, not a single-select combobox — worth remembering if `company_id` is ever seen non-null on a `components` row from before this fix, it's dead weight, not the real scoping mechanism.
- `jobs`/`commands` — `jobs.component_ids` is a JSON array of `ComponentRef` (`{type:'library', component_id, order, variable_values?}` or `{type:'inline', shell, script, timeout_seconds, order}`); `commands.payload` for a `run_script` command also carries `variables: Record<string,string>` (folded in by `resolvePayload` in `jobs.ts`), and `commands.warning` (bool) is set independently of `status` when a post-condition matches. `jobs.scheduled_at`/`expires_at`/`run_as_system` are now **live** (see "Scheduling" below) — no longer dead columns.

### ComStore
`origin='store'` components are seeded once via migration `0020` (a handful of trivial examples — clear temp files, flush DNS, list installed software) and are **read-only at the API layer** — `PATCH`/`DELETE` return 403 on a store-origin row. `GET /v1/admin/components/store` lists them (must be registered before `GET /:id` in Hono's route table, or `/store` gets swallowed as an `:id` match); `POST /:id/clone` copies a component (any origin) — including its variables and companies — into a fresh `origin='custom'` row a user can edit freely. This is intentionally a stub: no real marketplace/sharing mechanism, just the schema hook + a minimal browse+clone UI.

### Input variables
Full 4 types (String/Selection/Boolean/Date), matching Datto. Prompted per-job at creation time via the shared `dashboard/src/components/ComponentVariablePrompt.vue` — used by **two independent call sites** that each build a `ComponentRef`: `JobFormPage.vue` (formerly `CreateJobModal.vue`, deleted when Create Job moved to a full page — see "Scheduling" below) and `DeviceDetailPage.vue`'s Quick Job modal. Easy to miss one of these when touching this area again. All values pass through as strings regardless of declared type (Booleans become the literal strings `"true"`/`"false"`) — Datto's own convention, replicated rather than reinvented. Resolution happens server-side in `jobs.ts`'s `resolvePayload`: supplied value → the variable's `default_value` → (if `required`) a named 400 error before any commands are inserted. The agent (`agent/internal/executor/run.go`) injects the resolved map into `exec.Cmd.Env` via `append(os.Environ(), "KEY=value", ...)`.

### Post-conditions
A component's `post_conditions` (JSON array of `{id, stream: stdout|stderr|both, match_type: contains|regex, pattern, enabled}`) get evaluated in `worker/src/routes/checkin.ts`, at the exact point a command result is persisted (`worker/src/lib/postConditions.ts`'s `evaluatePostConditions`) — sets `commands.warning`, **never** touches `status`. Surfaced in `JobsPage.vue` as a distinct amber "Warning" mini-badge alongside the existing queued/sent/completed/failed ones.

### Scheduling ("assign at dispatch time", not "assign at creation time")

`POST /v1/admin/jobs` (`worker/src/routes/admin/jobs.ts`) branches on `type`:
- **`quick`** (default) — target devices resolve immediately, and `insertJobCommands` dispatches right away, same as the original design.
- **`scheduled`** — the job row is inserted with `scheduled_at`/`expires_at` set and **zero commands**. Nothing dispatches until the 2-minute cron's `dispatchDueScheduledJobs` (`worker/src/index.ts`'s `scheduled()` handler) finds it due. Target devices are resolved **then**, not at creation — a job created against "All Devices" today correctly picks up a device enrolled tomorrow, matching Datto's own documented behavior. A job with zero matching devices at a given tick is left `active` and retried every 2 minutes until it either resolves devices or expires. `cancelExpiredScheduledJobs` runs right after — any `scheduled`/`active` job whose `expires_at` has passed with **still zero commands** (i.e., it never got a chance to run) flips to `cancelled` instead of dispatching late. Both functions key off `NOT EXISTS (SELECT 1 FROM commands WHERE job_id = j.id)` as the "not yet dispatched" signal — no separate `dispatched_at` column needed.
- `insertJobCommands` is the one shared dispatch primitive both paths call — extracted from what used to be inline-only in the `POST /` quick-job branch.
- `run_as_system` now actually drives execution — see "Execution context ('run as a logged in user')" below.

- `JobFormPage.vue` (`/jobs/new`) — third real-world instance of the `.pf-page` full-page-form shell (after `PolicyFormPage.vue`, `ComponentFormPage.vue`). ### Execution context ("run as a logged in user")
`jobs.run_as_system` (default `true`) now actually drives execution, not just storage — the segmented control on `JobFormPage.vue`'s Execution section is no longer disabled. **v1 scope, confirmed via AskUserQuestion before building**: Windows only (`agent/internal/usersession` has no Linux/macOS implementation), console/active session only — not every RDS/AVD session, since a Job's `CommandResult` has one stdout/stderr/exit_code slot and fanning out to every active session would need a real protocol change — and PowerShell only (`resolveShell` already maps every Windows device to `powershell` for Jobs). A device with no console session, a non-Windows device, or a non-PowerShell shell value all fail the command with a clear `Stderr` message rather than silently falling back to a SYSTEM-context run, which would misrepresent what actually happened; this differs from `usersession`'s own "no active session is a normal no-op" philosophy for the tray, since a Job is something a technician explicitly asked to run.

- **The core problem this solves**: `usersession.RunAsSession` (`CreateProcessAsUser` under the hood) gives no stdout/stderr plumbing of its own, unlike `exec.CommandContext`'s `Stdout`/`Stderr` buffers used for the existing SYSTEM-context path. Rather than wiring raw pipe handles across the token boundary — the kind of fragile Windows-IPC surface this session already hit real friction with for the tray/reboot-marker work, which deliberately chose polled files over named pipes for the same reason — the *script content itself* is wrapped in a PowerShell redirect block (`& { <script> } 1> 'C:\Windows\Temp\beacon-<command_id>.out' 2> 'C:\Windows\Temp\beacon-<command_id>.err'`) before being written to the temp `.ps1` file. The outer process launch stays structurally identical to the SYSTEM-context path (`powershell.exe -NoProfile -NonInteractive -File <script>`), just invoked via `RunAsSession` instead of `exec.CommandContext` — no `cmd.exe` wrapper or its notoriously inconsistent `/c` quote-stripping involved at all.
- Relies on `C:\Windows\Temp`'s default Windows ACL, which grants `BUILTIN\Users` inheritable write rights that apply to new files regardless of which principal (SYSTEM or the logged-in user) creates them — the standard mechanism Windows itself uses for exactly this SYSTEM-service ↔ interactive-user handoff. **Not yet verified on real hardware** — a hardened/GPO-locked-down fleet that strips this default is a plausible real-world failure mode; if hit, the command fails loud (a permission error in `Stderr`), not silently.
- `agent/internal/executor/run.go`: `runScriptPayload` gained `RunAsSystem *bool` — a pointer, not a plain `bool`, so a JSON-absent field (every caller that predates this option: Quick Job, a direct single-device `POST /commands`) still defaults to `true`/system rather than silently flipping to run-as-user via Go's zero value. The temp-file-write+BOM logic was extracted into a shared `writeTempScript(shell, content)` helper reused by both paths.
- `agent/internal/executor/run_as_user_windows.go` (`//go:build windows`) is the real implementation: resolves the console session via `windows.WTSGetActiveConsoleSessionId()`, launches via `usersession.RunAsSession` unchanged (no signature change to that already-hardware-verified function — touching it would risk the tray's own verified path), then waits with a timeout via `windows.OpenProcess(SYNCHRONIZE|PROCESS_QUERY_INFORMATION|PROCESS_TERMINATE)` + `WaitForSingleObject` + `TerminateProcess` on timeout + `GetExitCodeProcess` — the same `OpenProcess`/`GetExitCodeProcess` pair the tray's own liveness check (`agent/internal/service/tray_windows.go`) already established as a working pattern in this codebase, just adding a blocking wait instead of polling. `run_as_user_other.go` (`//go:build !windows`) is a real, reachable stub, not dead code — a Job can target a mixed-OS fleet with one Execution setting, so a non-Windows device genuinely receives a `run_as_system: false` command.
- **Worker**: `insertJobCommands` (`worker/src/routes/admin/jobs.ts`) gained a `runAsSystem` parameter, included in each dispatched command's payload as `run_as_system` — threaded from both call sites (`POST /`'s quick-job branch, `dispatchDueScheduledJobs`). No migration needed — `jobs.run_as_system` already existed; the flag only needs to live in `commands.payload` JSON, which `checkin.ts` already relays generically.
- **Dashboard**: `JobFormPage.vue`'s Execution seg-bar is no longer disabled; `JobDetailPage.vue`'s Details card gained an Execution row (`detail.runAsSystem` was already typed/returned by the API, just unused in that page before this). Scope deliberately stays **`JobFormPage.vue` only, not the Quick Job modal** on `DeviceDetailPage.vue` — the Execution control has only ever existed on the full Job creation page.

### Requires Admin to Run (migration `0069`, added in a later session)

Distinct from the declined "Component access Levels" idea below — that was about *visibility* (Datto's 5-tier Basic→Super model for who can even see/edit a component), evaluated and correctly rejected as redundant with the existing 3-role RBAC. This is about *execution risk*: prompted directly by the user's own real-world concern — "anyone can run [components], right? ... a technician can't run potentially destructive components — it would need to go to an admin." Any technician can already create/edit/delete/run any component; nothing gated that before this.

`components.requires_admin` (bool, default `false`). Two scope decisions confirmed via AskUserQuestion before building:
- **Only an admin may set or clear the flag itself**, even though every other field on a component stays technician-editable as before — otherwise a technician could just un-flag a component they're not supposed to run, defeating the whole point. Enforced in `worker/src/routes/admin/components.ts`'s `POST /` and `PATCH /:id` (a `PATCH` is only rejected if `requires_admin` is actually *changing*, not merely re-sent at its current value, so a technician's routine edit of an unrelated field on a flagged component never trips this). `POST /:id/clone` carries the flag over as-is from the source — no bypass risk, since the clone ends up equally restricted, not un-flagged.
- **Technicians still see admin-only components everywhere** (library list, Job/Quick Job pickers) with a small amber "Admin Only" badge — transparent about what exists, just blocked from selecting/running it, not hidden.

**The one real enforcement point is `POST /v1/admin/jobs`**, not a new route — Quick Job (`DeviceDetailPage.vue`'s modal) was confirmed, by reading `submitQuickJob()`, to already dispatch through this exact same endpoint via a `ComponentRef`, so one check covers both the full Job Create page and Quick Job with no separate code path. Before any device resolution or command insertion, the route collects every `library`-type `component_id` referenced in the request and, if the requesting user isn't already an admin, queries which of them have `requires_admin=1` — any match 403s with the flagged component names listed, before any other work happens. `dispatchDueScheduledJobs` (the cron path for already-created scheduled jobs) needed no change — the check only matters at creation time, when a human is actually requesting the Job.

**Dashboard**: `ComponentFormPage.vue` gained a Requires Admin to Run toggle — a real seg-bar for an admin, a plain read-only line of text for a technician (`isAdmin` computed off `hasRole('admin')`), matching the "see it, can't change it" contract above. `ComponentsPage.vue`'s list, `JobFormPage.vue`'s Add Component flyout, and `DeviceDetailPage.vue`'s Quick Job library/store tabs all show the same small amber "Admin Only" badge next to a flagged component's name; the flyout/Quick-Job rows additionally swap the Add/Select button for a lock icon when the current user isn't an admin (client-side convenience only — the real gate is server-side, same defense-in-depth philosophy as every other consequential action in this codebase, e.g. Patch Management's approved-patches re-validation).

**Verified live end-to-end against local `wrangler dev` + a real technician session** (not just the admin break-glass token, since this feature is specifically about the technician/admin boundary): created a real local technician account, logged in for a genuine session token, and confirmed all four cases for real — a technician's attempt to create a component with `requires_admin: true` gets a 403; the same technician's attempt to run a Job with an existing flagged component gets a 403 naming it; an admin running that same Job succeeds (201, dispatched); and the technician's attempt to un-flag that component gets a 403, while editing an unrelated field on it (description) succeeds normally.

### Explicitly out of scope
- **Monitor** as a component category — Beacon's Policy/Monitor system already owns "run something and alert on it"; a future `component` policy check_type reusing this script library (floated in earlier sessions) is separate, later work.
- File attachments for Applications (no object storage/R2 configured yet — Applications behave identically to Scripts today, just a real, queryable category value).
- Component access **Levels** (Datto's Basic→Super 5-tier visibility) — redundant with Beacon's existing 3-role RBAC. (Not the same thing as "Requires Admin to Run" above — that's about execution risk, not visibility tiers; see that section.)
- **Notification (email on job completion)** — evaluated and declined for the Create Job page entirely (not even a disabled stub, unlike Execution before it was built) — Beacon has zero email-sending infrastructure anywhere (see Auth System's "no local password-reset email flow" note), and building that is a separate initiative, not a job-form add-on.
- **Full recurrence patterns** (daily/weekly/etc.) and Datto's "yearly calendar outlook" visual — `scheduled_at` supports exactly one future run, not a repeating schedule. Skipped for the same reason other elaborate reference visuals were skipped elsewhere (historical-metrics-over-time tab, etc.) — real complexity with no clear payoff at Beacon's current scale.

## Remote Shell / session system

The `sessions`/`SessionRelay` machinery predates this session (built as a generic shell/TCP-tunnel WS relay) but was never actually exercised end to end until the Interactive Remote Shell shipped — `POST /v1/sessions` had never been called by anything real before, which is exactly what let two real bugs (below) go unnoticed until now.

### Architecture
- `worker/src/durable-objects/session-relay.ts`'s `SessionRelay` DO is a **fully generic, byte-agnostic bidirectional relay** — forwards whatever bytes arrive from one tagged WebSocket role (`agent`/`client`) to the other, one DO instance per session (`idFromName(sessionId)`). It doesn't know or care about shell-vs-tunnel protocol semantics; that all lives in the agent/dashboard endpoints. This means a future tool (File Manager, etc.) can reuse this exact DO unmodified, just with a new `session_type`.
- `worker/src/routes/sessions.ts`: `POST /v1/sessions` (technician role) validates the device, generates a session ID + per-session random client auth token (see Auth System's "Remote-session WS auth"), inserts a `sessions` row, and queues an `open_session` command via the **existing command-queue channel** — the agent picks this up on its next normal check-in (up to 60s later), not a dedicated push mechanism. `GET /v1/sessions/:id/ws` upgrades and proxies straight to the DO.
- `sessions.sessionType` is a real SQL enum (`'shell' | 'tcp_tunnel'`), unlike the free-text `policy_monitors.check_type` pattern — adding a new session type needs a migration.
- `sessions.status` (`pending`/`active`/`closed`) exists in the schema but is **dead code** — inserted as `pending` and never transitioned anywhere. Not needed for the shell to work; left alone rather than wired up, since a real session-history/audit-log feature would be the natural reason to finally use it.

### Agent-side protocol (`shell.go`, rewritten this session)
One persistent PTY-backed shell process spawned per session (not one-shot-per-message, which is what shipped before this session and had zero real interactivity). Binary WS frames carry raw PTY bytes in both directions (keystrokes in; combined stdout+stderr out, since a PTY interleaves them naturally). Text WS frames carry a small JSON control envelope — currently just `{type:'resize',cols,rows}`. This binary-for-data/text-for-control split is deliberate and leaves room for future control messages without needing a new session type. Default shell: Unix picks `$SHELL` → `/bin/bash` → `/bin/sh`; Windows uses `powershell.exe` (matches the existing Quick Job "shell: auto" convention already documented elsewhere).

### Dashboard (`RemoteShellModal.vue`)
xterm.js (`@xterm/xterm` + `@xterm/addon-fit`) — first terminal-emulator dependency in this codebase. Opens a native `WebSocket`, shows a "Connecting… up to 60 seconds" state until the *first* message of any kind arrives from the agent side (there's no earlier signal without extra relay-side plumbing, since the agent doesn't attach until its next check-in). `term.onData` keystrokes are sent as binary frames; incoming binary frames are written via `term.write(new Uint8Array(...))` (not a manual UTF-8 decode, which risks corrupting multi-byte sequences split across chunks). A `ResizeObserver` on the terminal container drives both `FitAddon.fit()` and a resize control frame. Modal shell duplicates `.modal-backdrop`/`.modal`/`.modal-header`/`.btn-icon` CSS locally (matching this codebase's established per-component duplication convention — see STYLE.md) rather than sharing with `DeviceDetailPage.vue`'s differently-named `.modal-head`/`.modal-foot` variant.

### Two real bugs found and fixed while wiring this up (first time `/v1/sessions` was ever called from a browser)
1. **Missing CORS** — `/v1/sessions*` wasn't in `index.ts`'s CORS middleware list at all (only `/v1/admin/*` and `/v1/auth/*` were).
2. **Origin misdirection** — `sessions.ts` built the agent/client WS URLs from `new URL(c.req.url).origin`, which reflected the *production* domain even under local `wrangler dev` (caused by the `[[routes]]` custom-domain block in `wrangler.toml`) — a local test agent actually dialed out and connected to the real production worker during testing before this was caught. Fixed with a configured `WORKER_URL` env var (see Self-hosting config above) instead of deriving from the request.

### Explicitly out of scope (deliberate, not an oversight)
File Manager, Task Manager, Service Manager, Registry Editor, Event Viewer, Screenshot, remote takeover, shutdown/restart, network device deploy/wake, in-session Quick Jobs, session history/audit UI — all future work, all able to reuse this same relay/auth/dial-out plumbing. Multiple simultaneous shell sessions per device already "just works" (each gets its own DO instance) — a nice side effect, not a separate feature.

## Custom Fields

Beacon's equivalent of Datto RMM's "UDF" (User-Defined Field) system — scoped against the real Datto spec (300 fixed, pre-numbered, globally-relabeled slots, optionally agent-populated, usable as Job/Policy targeting criteria) and deliberately reduced for this pass, matching the codebase's established pattern of scoping down from Datto's exact feature shape when it doesn't add real value yet (see the Components/Job System's own "Explicitly out of scope" list for the same pattern elsewhere).

### Tables
- `custom_fields` — field definitions: `id`, `name` (display), `key` (identifier form, e.g. `ASSET_TAG` — migration `0030`, `''` means "not yet assigned, not script-referenceable"; partial-unique so multiple unset fields can coexist), `sort_order`, `created_at`. No per-scope/per-company restriction — every field is visible on every device, matching how Datto's UDF slots are always global.
- `device_custom_field_values` — `(device_id, field_id)` composite primary key, `value` (nullable text), `updated_at`. Both FKs `ON DELETE CASCADE` — deleting a field definition removes every device's stored value for it; deleting a device removes its values too. A real join table, not a JSON blob on `devices.inventory` — chosen so a future filter/targeting pass (see below) doesn't need a schema change.

### Scope decisions (all confirmed before implementation)
- **Dynamic named fields, not Datto's 300 fixed slots** — an admin creates exactly the fields they need instead of relabeling a fixed pool.
- **Manual entry only** — no agent-write path. Datto lets a script/monitor populate a UDF automatically ("populated by the Agent"); nothing in `agent/internal/executor` exists to write a field value back, and building that is separate work.
- **No Job/Policy targeting by field value** — Datto lets a Job or Policy target devices by UDF value (e.g. "Environment = Production"). Would need new filter logic in both `jobs.ts`'s target resolution and `alerts.ts`'s `deviceMatchesPolicy`; deferred rather than bundled in. Distinct from the script-variable capability below — a script can *read* a field's value once dispatched to a device, but a field's value can't yet be used to *decide which devices* a job/policy targets in the first place.

### Script variables (`CF_<KEY>`) — Datto UDF-style, reference-by-name

A component's script can reference a device's custom field value directly, with no per-component declaration step — researched against Datto's real docs (rmm.datto.com), which distinguish this from Input Variables (Beacon's `component_variables`, declared per-component, prompted at job-creation time, one value for the whole job) via a genuinely separate mechanism: `UDF_1`..`UDF_300`, referenced by fixed naming convention directly in the script body, resolved *per-device* at dispatch time. Beacon's version: `${CF_<KEY>}` (bash), `$env:CF_<KEY>` (PowerShell), `%CF_<KEY>%` (Batch) — `CF_` prefix chosen for the same reason Datto's `UDF_` prefix exists, namespacing against an unrelated `component_variable` of a similar name.

- **Resolution stays inside `insertJobCommands`** (`worker/src/routes/admin/jobs.ts`) — the one shared dispatch primitive both `dispatchDueScheduledJobs` and the quick-job `POST /` handler already call, so one change covers both paths, exactly like `target_os` filtering already does per-device there. A new `fetchCustomFieldVars` helper bulk-fetches every target device's values in one `WHERE device_id IN (...)` query (same placeholder-list shape `resolveDevices` already uses) — early-exits with zero extra queries when no field has a `key` assigned yet, and never injects a `CF_<KEY>` env var for a device/field pair with no stored value (no empty-string vars). Merged into each device's `variables` map as `{...cfVars, ...payload.variables}` — a component's own declared `component_variables` value wins on the (extremely unlikely) literal collision.
- **No agent-side change** — `agent/internal/executor/run.go` already treats `commands.payload.variables` as an opaque flat `map[string]string`, blindly `append`ing every key as `KEY=value` to the child process env. Purely a worker-side merge before serializing the payload.
- **Rename guard, not a hard lock**: `PATCH /v1/admin/custom-fields/:id` blocks a `key` change if any `components.script` still contains the literal `CF_<OLDKEY>` substring — returns `409` with the list of blocking component names/ids, rather than silently breaking a script that references the old key. Deliberately a **plain JS substring scan** over all `components.script` (`SELECT id, name, script FROM components`, then `.includes()`), not SQL `LIKE` — key values contain `_`, which SQLite's `LIKE` treats as a single-char wildcard, so a `LIKE '%CF_<oldKey>%'` query would false-match unrelated scripts. Full-table scan is fine at this scale (self-hosted admin action, tens not thousands of components). Renaming to/from an empty key, or changing `name`/`sort_order` without touching `key`, is never blocked.
- Key format: `^[A-Z_][A-Z0-9_]*$` (uppercase-only — stricter than `component_variables`' mixed-case `VARIABLE_NAME_RE`, since env var convention is uppercase and this is auto-derived from the display name anyway), validated both client- and server-side since the literal `CF_<KEY>` string is what ends up embedded in scripts.

### Worker
- `worker/src/routes/admin/custom-fields.ts` — field-definition CRUD (`GET/POST /`, `PATCH/DELETE /:id`). **Admin-only**, not `technician` — this is Settings-area configuration (same tier as SSO providers, unlike routine per-device mutations). `POST`/`PATCH` also validate/uniqueness-check `key` and run the rename guard described above.
- `worker/src/routes/admin/devices.ts` — `GET /:id/custom-fields` (readonly) returns every field definition left-joined against this device's stored values (`null` when never set); `PATCH /:id/custom-fields/:fieldId` (technician) upserts a value — checks for an existing row, then inserts or updates, since no `onConflictDoUpdate` precedent existed elsewhere in the codebase to follow.
- `dashboard/src/api.ts`'s `request()` now parses a JSON `{error}` response body into the thrown `Error`'s message when present, falling back to the raw response text otherwise — added so the rename guard's 409 message (and its component list) reads cleanly in the UI instead of a raw JSON blob; backward-compatible with every other existing error banner in the app.

### Dashboard
- `CustomFieldsSettingsPage.vue` (`/settings/custom-fields`, admin only) — manages field definitions: inline-editable name (`@change`, same convention as the device page's Warranty field), a Key column (auto-suggested from the name as you type — uppercase, non-alnum runs → `_` — editable before save, stops auto-suggesting once hand-edited), ↑/↓ buttons that swap two fields' `sort_order` and persist both immediately. A blocked key rename reverts the input to its prior value and surfaces the 409 message in the existing `.error-banner`. Modeled directly on `SsoSettingsPage.vue`'s "Group → Role Mappings" list section (`.pf-monitors`/`.pf-mon-row`/`.pf-tbl-head` classes reused as-is).
- `DeviceDetailPage.vue` gained a **Custom Fields** section between Network and Security (matching Datto's own relative UDF placement — second-to-last, just before Security). One inline-editable text input per field definition; values load alongside everything else in `onIdChange`'s `Promise.all`. Editing a field calls `PATCH /v1/admin/devices/:id/custom-fields/:fieldId` directly — no separate save step.
- `ComponentFormPage.vue` fetches the field list once on mount and shows a small discoverability hint under the Script textarea (`Available custom fields: CF_ASSET_TAG, CF_SITE_CONTACT`, only fields with a non-empty `key`) — matches the existing placeholder hint's own "Reference variables as..." text. No autocomplete/insertion, purely informational.
- **State-declaration-order gotcha**: the `customFields`/`customFieldsLoading`/`customFieldSaving` refs must be declared *before* `onIdChange` and the router `watch(..., { immediate: true })` that calls it — that watch fires synchronously during `<script setup>` execution, so any ref it reads must already be initialized textually above it. Declaring them near the bottom of the file (next to unrelated code, e.g. the Warranty-field logic) throws a TDZ `Cannot access '<name>' before initialization` on every page load — a real bug hit once, invisible to `vue-tsc` since it's a runtime evaluation-order issue, not a type error. Fixed by keeping all section-state refs grouped together above `onIdChange`, alongside `auditData`/`deviceAlerts`/`effectiveMonitors`.

## Company Variables / Secrets

Per-Company key/value config, referenceable from component scripts as `CV_<KEY>` — Cloudflare-Workers-variables/-secrets-style (also matches GitHub Actions' variables/secrets split), the feature that originally motivated the Tenant→Company terminology rename (see Terminology note above). Distinct from Custom Fields: Custom Fields are per-device values on a global set of field definitions; Company Variables are per-company, with no cross-company definition sharing at all — the same `key` can independently exist (with different values) on multiple companies.

### Scope decisions (confirmed via AskUserQuestion before implementation)
- **Company-level only, no Location-level override** — confirmed early in the terminology discussion that prompted this feature ("we don't need location level variables, they still fall under the company").
- **Two kinds, not one** — plain **Variables** (cleartext, always visible/editable) and **Secrets** (AES-GCM encrypted via `CONFIG_ENCRYPTION_KEY`, write-only after saving) — matching the Cloudflare Workers vars/secrets model the user referenced directly, rather than treating every value as sensitive by default.
- **`CV_<KEY>` prefix** — distinct from Custom Fields' `CF_<KEY>` and `component_variables`, no collision risk.

### Table
`company_variables` (migration `0061`) — `id`, `company_id` FK `ON DELETE CASCADE`, `key`, `is_secret`, `value` (cleartext, only when `!is_secret`), `value_ciphertext`/`value_nonce` (only when `is_secret` — same `encryptSecret`/`decryptSecret` AES-GCM helper `sso_providers`/`email_settings` already use), `description`, timestamps. `UNIQUE(company_id, key)`. A secret's plaintext is **never** returned by any read endpoint once saved — API responses report `hasValue: boolean` in its place, same "secret never returned, blank input means keep existing" contract as SSO/email provider config.

### Resolution at job dispatch (`worker/src/routes/admin/jobs.ts`)
`fetchCompanyVariables()` bulk-fetches every targeted company's variables in one query (`WHERE company_id IN (...)`, keyed by `company_id`) and decrypts every secret once here — not per-device, since a company variable's value is identical for every device under that company, unlike Custom Fields' genuinely per-device values. Called from `insertJobCommands` (the one shared dispatch primitive both `dispatchDueScheduledJobs` and the quick-job `POST /` handler already call — same place `fetchCustomFieldVars` already hooks in), merged into each device's `variables` map as `{...cvVars, ...cfVars, ...payload.variables}` — a component's own declared variable always wins on the (extremely unlikely, given the `CV_`/`CF_` prefixes) literal collision. `insertJobCommands`/`dispatchDueScheduledJobs` both gained a `configEncryptionKey` parameter for this (threaded from `c.env.CONFIG_ENCRYPTION_KEY` / `env.CONFIG_ENCRYPTION_KEY` at both call sites, including `index.ts`'s `scheduled()` handler) — no agent-side change needed, this is purely a worker-side merge before serializing the payload, same shape as the `CF_<KEY>` merge it sits alongside.

### Worker
`worker/src/routes/admin/companies.ts` gained nested `/:id/variables` (`GET`/`POST`/`PATCH /:id`/`DELETE /:id`). All four operations are admin-only: even a non-secret value is part of the same dispatch-time configuration namespace as secrets, and technicians must not be able to enumerate or alter that namespace. Key format validated server-side (`^[A-Z_][A-Z0-9_]*$`, same regex as Custom Fields). `PATCH` never accepts a `key` change (delete + recreate instead — no rename-guard precedent needed here since nothing else references a Company Variable by database id, only by the `CV_<KEY>` string baked into a script).

### Dashboard
`CompaniesPage.vue`'s existing per-company expand-row (Contacts/Locations/Tokens tabs) gained a 4th admin-only **Variables** tab, same list/modal shape as Contacts. The tab is not rendered or fetched for technicians/readonly users; the backend remains the actual enforcement boundary. Add/Edit modal: Key (disabled once created — uppercased/sanitized as-you-type on create), a Secret toggle (disabled once created — a variable can't change kind after the fact), Value (`type="password"` when secret, placeholder says "Leave blank to keep the current value" when editing), Description. List row shows `CV_<KEY>` + a "Secret" badge when applicable; secret rows show `•••••••• (configured)`/`Not set`, never the plaintext. `ComponentFormPage.vue` gained a short discoverability note near the existing Custom Fields hint under the Script textarea — deliberately doesn't enumerate actual keys the way the Custom Fields hint does, since a component can be scoped to multiple companies with different Variable sets, unlike Custom Fields' single global definition list.

## Network Discovery

v1: a live-host sweep only — scoped against Datto RMM's Network Discovery as reference, but deliberately reduced. Confirmed via AskUserQuestion before implementation: **ping sweep + ARP table cross-reference, no credentialed WinRM/SSH/SNMP fingerprinting** (real Datto-parity value, but a much bigger cross-platform protocol-client lift with no existing precedent in this codebase — Company Variables remains the natural home for scan credentials whenever that's added, an Icebox item, not v1); **list only, no new alert channel** (a discovered host has no `device_id`, and the existing webhook/email machinery is built around one); **one probe device per company** (matches the "chosen" singular framing from the original scoping discussion — a multi-Location company needing separate scanners per site is a natural v2 extension).

### Architecture: dispatched through `commands`, not the check-in wire protocol
Scans dispatch through the existing `commands` table — the same one-shot mechanism already used for `install_patches`/`run_audit`/`uninstall_agent` — deliberately not through `CheckInRequest`/`CheckInResponse`. This was a direct lesson from this same session's production incident (a wire-protocol field rename broke check-in fleet-wide): extending the check-in wire protocol is exactly the wrong surface to add new functionality to when a config-driven, one-shot-per-device dispatch model (which Patch Policy already proves out) fits just as well and touches zero shared wire types. `dispatchDueDiscoveryScans` (cron, mirrors `dispatchDuePatchPolicies`'s shape) inserts a `commands` row (`type: 'network_scan'`) targeted at a company's designated probe device once `scan_interval_minutes` has elapsed since `last_scanned_at`. The agent picks it up via its already-existing generic per-command goroutine dispatch loop, runs the scan, and JSON-encodes the result straight into the existing `CommandResult.Stdout` field — the same trick `install_patches`' `wuinstall.Result` already uses. `worker/src/routes/checkin.ts`'s existing `pending_command_results` loop gained one new branch: a completed `network_scan` command's `Stdout` gets parsed and upserted into `discovered_devices`.

**Deliberately no reuse of `devices.agentType`/`'discovery_probe'`** — that enum has existed since day-one schema scaffolding (`migrations/0000`) but was never read or branched on anywhere in worker, agent, or dashboard code before this feature. `network_discovery_configs.probe_device_id` is the single source of truth for which device scans; mutating `agentType` in parallel would just be a second, syncable-out-of-date label for the same fact — the "fake toggle" pattern this codebase already avoids elsewhere (see Branding's Product Name reasoning). `agentType` remains unused scaffolding.

### Tables (migration `0062`)
- `network_discovery_configs` — one row per company (`company_id` `UNIQUE`), `probe_device_id` FK, `enabled`, `cidr_ranges` (JSON string array), `scan_interval_minutes` (default 360 = 6h — a plain recurring interval, not Maintenance/Patch Policy's weekly-window model, since this wants continuous periodic checking rather than a specific maintenance window), `last_scanned_at`.
- `discovered_devices` — keyed by `(company_id, ip_address)`, not MAC — simpler upsert, with the known, honestly-documented tradeoff that a DHCP-reassigned IP can appear as a "new" device. `mac_address`/`hostname` nullable (MAC only resolvable when the probe and target share an L2 segment; ARP doesn't cross routers). `first_seen_at`/`last_seen_at`/`times_seen` build the "baseline over time" the original scoping discussion wanted. `dismissed` lets a technician quiet a recognized-but-unmanaged device (a printer, a switch) without deleting its history. **No automatic correlation against already-enrolled Beacon devices** — would need MAC-matching against audit-collected NIC data, real complexity, deferred; a technician manually dismisses entries they recognize.

### Worker (`worker/src/lib/discovery.ts`, nested routes on `worker/src/routes/admin/companies.ts`)
- `dispatchDueDiscoveryScans(db, now)` — re-verifies the probe device still exists/is `approved`/still belongs to the company before dispatching (skip silently, retry next tick, if not — same defensive shape `dispatchDuePatchPolicies` uses for its own targeted devices), inserts the `commands` row, stamps `last_scanned_at`. Called from `index.ts`'s `scheduled()` alongside the other cron dispatch functions.
- `GET/POST /v1/admin/companies/:id/discovery` — get/upsert the config. `POST` validates `probe_device_id` belongs to this company, is `status = 'approved'`, and its effective class (`overrideClass ?? detectedClass`) is not `'laptop'` — 400 otherwise, directly enforcing "always-on server or workstation, no laptops" from the original scoping. CIDR ranges validated both for syntax and size — capped at `/20` or smaller (4096 addresses); a broader range would be catastrophic for a periodically-repeating scan to walk. The agent independently re-caps the same limit as defense in depth, since a payload reaches it via `commands` with no further validation at dispatch time.
- `POST /v1/admin/companies/:id/discovery/scan-now` — the "no fallback needed, just run next cycle or manually trigger" behavior from the original scoping. Looks up the saved config and dispatches immediately, same insert shape as the cron path.
- `GET/PATCH/DELETE /v1/admin/companies/:id/discovered-devices[/:deviceId]` — list/dismiss/delete.
- `recordDiscoveredHosts()` (called from `checkin.ts`) — check-then-insert-or-update by `(company_id, ip_address)`, same convention as Custom Fields' device values. A scan that doesn't resolve MAC/hostname this cycle (e.g. an ARP cache miss) never blanks out a value a previous scan already found — only overwrites when the new scan actually found something.

### Agent (`agent/internal/discovery`, new `network_scan` command in `agent/cmd/agent/main.go`)
`Scan(cidrRanges []string) Result` — same "shell out to the platform's native tool + regex the stdout" convention `pingutil`/`hardware.go` already establish (raw ICMP/ARP needs elevated privileges on Unix). Three phases:
1. **Bounded-concurrency ping sweep** (32 workers) — a fast, single-packet liveness check with a short (~1.2s) timeout, deliberately **not** `pingutil.Ping`: that function's ~12s+ deadline is calibrated for "check one specific host I expect to be healthy," where a timeout is rare — a sweep's common case is the opposite (most addresses in a typical range are unused), so reusing it would make a scan take many minutes longer than necessary.
2. **One ARP table dump** (`arp -a` on Windows/macOS, `ip neigh show` on Linux — three platform-specific stdout parsers) run once after the sweep, not per-host, parsed into an IP→MAC map.
3. **Best-effort reverse DNS** (`net.LookupAddr`, 500ms timeout) per responding host — swallows failure, never blocks or fails the rest of the scan (same "one collector's failure shouldn't block the others" convention the audit collectors already follow).

A single `Scan` call is bounded to `maxHostsPerScan = 4096` total addresses across every requested range (mirrors the worker's own `/20` cap) and an overall 5-minute budget, same pathological-run guard as `filesize.Measure`'s `walkBudget`. No protocol type changes needed anywhere — payload/result both ride the existing generic `Payload json.RawMessage`/`Stdout string` fields on `Command`/`CommandResult`, exactly like `install_patches`.

### Dashboard
`CompaniesPage.vue`'s existing per-company expand-row gained a 5th **Discovery** tab, alongside Contacts/Locations/Tokens/Variables. Unlike those (a flat list), this tab holds two genuinely different concerns laid out as stacked sections: **Scan Configuration** (probe device `<select>`, client-side filtered to this company's own approved non-laptop devices — mirrors the server-side validation; repeatable CIDR range inputs; interval `<select>`; Enabled toggle; Save; "Scan Now", disabled until a config exists) and **Discovered Devices** (a table — IP/MAC/Hostname/First Seen/Last Seen/Times Seen/Dismiss/Delete — with a "hide dismissed" filter). No new sidebar entry, consistent with the other four tabs. (See the Icebox's "Dedicated per-Company page" entry — this is exactly the kind of feature that could tip the balance toward building one, if this tab ever starts feeling cramped.)

## Device Groups

Beacon's equivalent of Datto RMM's "Groups" — a static, manually-curated, named collection of individual devices, usable to target both Jobs and Monitoring Policies. Researched directly against Datto's real Filters/Groups spec (rmm.datto.com) this session: Datto actually has two distinct mechanisms — **Filters** (dynamic, criteria-based, auto-updating membership across ~85 possible attributes) and **Groups** (static, manually-curated). Beacon builds only the Groups half.

### Scope decisions (all confirmed before implementation)
- **No dynamic Filters** — the actual need was "hold a named, reusable set of specific machines," not a live-query engine. A Filter would need real new infrastructure (a criteria builder, `WHERE`-clause evaluation at dispatch time) for a capability not being asked for.
- **No "Company Groups"** (a saved collection of whole companies) — `JobFormPage.vue`'s target flyout already supports adding multiple companies to one job today; a saved company-group would only be a naming convenience for something that already works, not new capability.
- **Flat and global** — a device can belong to more than one group; groups aren't scoped to a company.
- **Usable to target both Jobs and Policies** — matches Datto's own dual usage (its docs confirm Monitoring Policies target through either Device Filters or Device Groups, with OR logic across multiple targets).
- **"Device Groups" label everywhere in the UI, never bare "Groups"** — `components.category` is already surfaced in the UI as "Group" (a different concept — component organizational tags); bare "Groups" would collide with that existing term.

### Tables
- `device_groups` — `id`, `name`, `description`, `created_at`, `updated_at`.
- `device_group_members` — `(group_id, device_id)` composite PK (migration `0031`), both FKs `ON DELETE CASCADE`. A pure association with no independent row identity ever referenced, so composite PK is the better fit than `component_companies`' synthetic-id + separate `UNIQUE` constraint pattern — matches the more recently-established `device_custom_field_values` convention.
- `policy_groups` — `(policy_id, group_id)` composite PK. As of migration `0032` this is one of three OR'd targeting dimensions (alongside `policy_companies`/`policy_devices`) rather than the sole one — see "Policy Targeting (Companies/Devices/Groups)" below for the current full model.

### Job targeting
A 4th `resolveDevices()` branch in `worker/src/routes/admin/jobs.ts` (alongside the existing `devices`/`companies`/`all`) — `JOIN device_group_members`, `DISTINCT` (so targeting overlapping groups, or a device in more than one targeted group, doesn't double-dispatch), still filtered to `status='approved'`. No migration needed on `jobs` itself — `target_type`/`target_ids` are already unconstrained TEXT/JSON columns, same as when `companies` targeting was added. Both `dispatchDueScheduledJobs` and the quick-job `POST /` handler flow through this one function, so group targeting works for both dispatch paths automatically.

### Policy targeting — the performance-sensitive part
`worker/src/lib/alerts.ts`'s `deviceMatchesPolicy`/`matchMonitorsForDevice` gained a device's group-ID set and a policy-ID→group-IDs map, both **always pre-fetched by the caller, never queried inside a per-device loop** — this path runs on real hot paths (every device check-in, the 2-minute offline cron over the whole fleet). `fetchPolicyGroupIds`/`fetchDeviceGroupIds` helpers follow the exact same "fetch once per invocation" rule `fetchEnabledPolicyMonitors` already established: `resolveEffectiveMonitors`'s check-in path (called once per device every 60s) fetches both maps for just that one device; `evaluateOfflineAlerts` (the bulk cron) fetches both maps **once for the whole tick**, before its device loop, not per device. `reconcileOrphanedAlerts` (already existing, already called from `policies.ts` whenever `target_os`/`target_class` narrows) bulk-fetches for just its affected rows. Migration `0032` (see below) extended this exact same fetch-once pattern with two more maps (`policyCompanyIds`/`policyDeviceIds`) rather than inventing a new one.

### Worker
- `worker/src/routes/admin/groups.ts` (new) — group CRUD (`GET/POST /`, `PATCH/DELETE /:id`) and nested membership (`GET/POST /:id/members`, `POST /:id/members/bulk` for the `DevicesPage.vue` bulk action, `DELETE /:id/members/:deviceId`). **`technician` for mutations, `readonly` for viewing** — Device Groups are operational targeting infrastructure like Jobs/Policies, not Settings-area config like Custom Field *definitions*/SSO (which are admin-only). `GET /` and `GET /:id` both include `deviceIds: string[]` per group (via `group_concat` on the list route) so the dashboard can compute accurate deduped device counts without an extra request per group.
- `worker/src/routes/admin/policies.ts` gained nested `/:id/groups` (`GET`/`POST`/`DELETE`), mirroring `components.ts`'s `/:id/companies` shape.

### Dashboard
- `GroupsPage.vue` (`/groups`) — list page mirroring `ComponentsPage.vue`/`CustomFieldsSettingsPage.vue`.
- `GroupFormPage.vue` (`/groups/new`, `/groups/:id`) — reuses `ComponentFormPage.vue`'s "Add Company" flyout convention verbatim, adapted to search/add/remove devices instead of companies.
- `DevicesPage.vue` gained an "Add to Group" bulk toolbar action (next to the existing `bulkAudit`/`bulkEndMaintenance`), using the page's pre-existing bulk-select infrastructure (`selected`/`selectedCount`/`selectedIds`) — pick an existing group or name a new one, then `members.addBulk`.
- `JobFormPage.vue`'s target flyout gained a 4th `TargetItem` kind (`group`) and flyout category ("Device Groups") — `isTargeted`/`toggleTarget` needed no changes (already generic over kind/id); only the template branch, `submit()`, `targetLabel`, and `resolvedDeviceCount` needed a new case each, the same shape of change adding `companies` targeting already was.
- `PolicyFormPage.vue` originally gained a standalone "Device Groups" section here (independent lifecycle, its own API calls) — **superseded by migration `0032`'s unified Targets section**, see below.
- Sidebar: "Device Groups" link lives in the **Devices** section (alongside Device Approvals/All), not Automation — groups organize devices, they don't do anything by themselves the way Jobs/Components do.

## Policy Targeting (Companies / Devices / Device Groups, migration 0032)

Redesigned to match a real Datto Create Policy reference: one unified "Targets" section (a single Add Target flyout, one flat list) — Beacon previously split this three ways: a Scope seg-bar (Global/single-Company combobox), OS/Class pill checkboxes, and a separate Device Groups picker.

### Scope decisions (confirmed via AskUserQuestion before implementation)
- **Unify Companies (now multi-company, not one), individual Devices (new), and Device Groups into one Targets flyout**, reusing `JobFormPage.vue`'s `.tf-` flyout pattern verbatim for visual/interaction consistency with the rest of the app.
- **OS/Class targeting stays separate and unchanged** — its own section (relabeled "OS & Class" to free up the word "Targets"), still ANDed with everything else. Not folded into the new flyout as a fake "Device Filters" category, since Beacon deliberately has no dynamic Filters (see Device Groups' own scope decisions above).
- **Targeting is a heterogeneous OR-list, not Job's single-kind-exclusive model.** This is the one genuine behavioral fork from `JobFormPage.vue`'s flyout, worth remembering since the two flyouts now *look* identical but behave differently: Job's flyout restricts to one target kind at a time (picking a Device clears any previously-picked Companies) — Policy's flyout does **not**; a policy's Targets list can mix a Company AND a Device AND a Device Group simultaneously, and a device qualifies if it matches **any** entry, of **any** kind. Confirmed via AskUserQuestion against this project's own prior research into Datto's real documented behavior ("OR logic across multiple targets," already noted above under Device Groups) rather than assumed from `JobFormPage.vue`'s precedent.
- Zero targets across all three tables = unrestricted (matches every device) — generalizes the pre-existing "zero `policy_groups` rows = unchanged" precedent to all three kinds uniformly.
- Per-target Enabled/Disabled overrides (a distinct Datto capability shown in a second reference screenshot — temporarily excluding specific companies/devices from an otherwise-matching policy) — explicitly declined for this pass, no Beacon equivalent exists.

### Tables
- `policy_companies` — `(policy_id, company_id)` composite PK, migration `0032`, mirrors `policy_groups`' exact shape. Supersedes the old single `policies.company_id` — a policy can now target multiple companies, not one.
- `policy_devices` — `(policy_id, device_id)` composite PK, migration `0032` — individual-device targeting, previously not possible for policies at all (only Jobs had it).
- `policies.scope` (`'global'|'company'`) is now **derived, not directly user-set** — recomputed by `recomputePolicyScope()` (`worker/src/routes/admin/policies.ts`) after every mutation of any of the three target tables: `'global'` when a policy has zero targets across `policy_companies`/`policy_devices`/`policy_groups`, `'company'` when it has 1+. Purely a display/tab-filtering convenience (`GlobalPoliciesPage.vue`'s Global/Company tabs, `DeviceDetailPage.vue`'s scope badge) — the actual matching logic (`deviceMatchesPolicy`) reads the three tables directly and never looks at this column. `policies.company_id` is now fully vestigial, same fate as `components.company_id` after migration `0022`.

### Matching logic (`worker/src/lib/alerts.ts`)
`deviceMatchesPolicy` no longer has a `scope==='company' && policy.companyId!==device.companyId` AND-check at all — that dimension folded into the OR-list. New `fetchPolicyCompanyIds`/`fetchPolicyDeviceIds` helpers (same whole-table-fetch-once-per-invocation shape as `fetchPolicyGroupIds`) get threaded through the same four call sites `fetchPolicyGroupIds` already reaches (`resolveEffectiveMonitors`, `evaluateOfflineAlerts`, `reconcileOrphanedAlerts`, and `matchMonitorsForDevice` itself) — no new call sites, no change to the "fetch once per invocation, never per device" hot-path rule. A device matches a policy's targeting if `companies.size + devices.size + groups.size === 0` (unrestricted) OR `device.companyId ∈ companies OR device.id ∈ devices OR (any of device's groups) ∈ groups` — still ANDed with the separate OS/Class check.

### Worker
- `worker/src/routes/admin/policies.ts` gained `/:id/companies` and `/:id/devices` (`GET`/`POST`/`DELETE`), mirroring the pre-existing `/:id/groups` triplet exactly — same role tiers (`technician` mutate, `readonly` view), same "POST skips `reconcileOrphanedAlerts` (widening only), DELETE calls it (can narrow)" rule. The pre-existing `/:id/groups` POST/DELETE handlers gained a `recomputePolicyScope()` call each — a real gap closed, not just new code, since they never touched `scope` before this migration (harmless when `scope` was company-only, incorrect once groups became one of three dimensions).
- `GET /v1/admin/policies` gained `companyIds`/`deviceIds`/`groupIds` (string arrays) per policy, fetched via `inArray(policyId, ids)` batch queries alongside the existing `monitors` fetch in `listWithMonitors` — same "fetch once for the whole list, merge in TS" shape that function already used for monitors, just extended to the three target tables. `companyIds` is the load-bearing one (needed by `GlobalPoliciesPage.vue`'s companyMode filter below); all three included for symmetry.
- `POST /` no longer accepts `scope`/`company_id` in the body — policies always start with zero targets (`scope: 'global'`), Targets are added via the nested routes afterward, same "create empty, then POST nested items" convention every other nested resource in this codebase already follows (Companies/Variables on Components, Monitors/Groups on Policies). `clone_from` now also copies the source's `policy_companies`/`policy_devices`/`policy_groups` rows (parity with monitors), then calls `recomputePolicyScope` rather than copying `source.scope` directly.

### Dashboard
- `PolicyFormPage.vue` — the old Scope seg-bar + single-company combobox is gone entirely. A new "Targets" section (`.tf-overlay`/`.tf-panel` flyout, copied from `JobFormPage.vue`'s markup/CSS per this codebase's duplication convention, **but with `toggleTarget()` rewritten as a flat push/remove — not Job's kind-switch-clears-others logic**) replaces both the old Scope picker and the old standalone Device Groups block. Use a check type with no seeded collision (`ping`, `file_size`, etc.) for a clean signal.

## Patch Management

Windows Update integration, built in deliberate slices matching this codebase's established scoping pattern (see Components/Job System's ComStore, Device Groups, etc.): **Patch Visibility** (scan+report only), then **approval workflow** (fleet-wide approve/ignore), then **install capability** (actually installing approved patches), then **Patch Policy** (auto-approval rules + scheduled recurring install windows) — see below.

### Patch Visibility (scan+report)
- `agent/internal/audit/patches.go`'s `collectPatches()` — Windows-only (matches Datto RMM's own Patch Management scope), runs as part of the regular audit. Uses the native `Microsoft.Update.Session` COM API via PowerShell (`CreateUpdateSearcher().Search("IsInstalled=0 and IsHidden=0 and Type='Software'")`) — no `PSWindowsUpdate` module dependency, and searching (not installing) needs no admin rights. `Type='Software'` deliberately excludes driver updates. A 180s context timeout, well past every other collector's usual 15s, since WUA search can genuinely take 10-90+ seconds on a first run or WSUS-backed box.
- "Definition Updates" (Defender AV signature packages) are filtered out client-side after the search, not via the WUA query string — `IUpdateSearcher`'s criteria language only supports `CategoryIDs` by GUID, not friendly names. Without this, a fully-patched machine still shows a permanently-recurring pending "Security Intelligence Update," which isn't something an admin manages through a patching workflow.
- Rides the existing `device_audits` JSON-blob-per-category pattern (migration `0052`, `patches` column) — no dedicated table, one array per device's latest audit, same as `hardware`/`software`/`services`/`security`. Not diffed into `device_audit_changes` (no `'patches'` category exists there) and not stripped in privacy mode (only `software`/`services` are).
- **`omitempty` wire bug, found and fixed live in a later session**: `AuditPayload.Patches` (`agent/internal/protocol/types.go`) had `json:"patches,omitempty"` — `encoding/json`'s `omitempty` treats any zero-length slice as empty regardless of nil-ness, so a genuinely successful scan that correctly filtered its one pending item (a Defender Definition Update) down to zero real patches produced the exact same omitted-field wire shape as "collection failed" or "not Windows" (both a plain nil `Patches`) — both landed as `patches: null` in the stored audit, indistinguishable on the dashboard from "never scanned." `DeviceDetailPage.vue`'s empty-state text (`"No pending patches — device is fully up to date, or no audit data yet."`) already honestly hedged on this, which is what surfaced the question in the first place. Root-caused live: dispatched the exact production `collectPatches` PowerShell logic directly against a real device via `run_script`, confirmed it returns a clean `{"Updates":[],"Error":null}` (zero-error, zero-result), while the actual stored audit — built from the old wire format — still showed `patches: null`. Fixed by dropping `omitempty` (worker needed no change — `payload.patches ? JSON.stringify(payload.patches) : null` in `audit.ts` already handled `undefined`/`null`/array correctly, the agent just never gave it a real empty array to see): a nil slice still serializes as explicit `null` (collection error / non-Windows, unchanged), a non-nil empty slice now serializes as `[]` (a real "fully patched" answer). Devices need to pick up a new agent build via self-update for this to take effect — until then, `null` on an old agent still carries the old ambiguity.
- `GET /v1/admin/devices/:id/audit/latest` is the only read surface — returns the whole latest audit row, patches included, any role. No dedicated `/patches`-per-device endpoint.
- `DeviceDetailPage.vue`'s Patches section sits between Software and Services in nav order — flat list (no grouping by category), each row: title, `KB123, KB456` join, severity badge (`Critical`→danger, `Important`→warn, else muted), categories as plain text. Pagination only, no filter/sort.

### Approval workflow (migration `0053`)
Confirmed via AskUserQuestion before building: approval is **fleet-wide, not per-device** — one decision per Windows Update, applying everywhere it's detected, matching how Datto RMM and real-world patch management actually works (you're deciding whether an update is safe to roll out, not re-deciding it machine by machine). Simpler schema than a per-device state table would need, too.

- **Stable identity was the real prerequisite**: patches had no persisted key before this — `PatchItem` only carried `Title`/`KBArticleIDs[]`, neither guaranteed unique or stable. `agent/internal/audit/patches.go` now also captures WUA's own `$update.Identity.UpdateID` GUID (`PatchItem.UpdateID`, `omitempty` — empty on pre-upgrade agents). **A patch entry with no `update_id` can't be approved** — the worker surfaces a `needsRescan` count instead of erroring, and the dashboard shows a "needs a rescan" note rather than a broken button. Existing already-scanned fleet data has no `UpdateID` until devices update again and re-audit — same "code merged ≠ deployed" gap as every other agent-side change.
- `patch_approvals` — `update_id` primary key, `status` (`'approved'|'ignored'`), plus a `title`/`kb_article_ids`/`severity` **snapshot** taken at approval time for display. No row = pending/undecided, same "absence means default state" convention as `policy_monitors.notify_webhook`. The live "which devices currently have this pending" answer always comes from devices' latest audits, never from this table.
- `worker/src/routes/admin/patches.ts` (mounted at `/v1/admin/patches`): `GET /` (readonly) fetches every `approved` device's latest non-null-patches audit (one query per device, fine at self-hosted scale — same reasoning as the Custom Fields rename guard's full-table scan), groups by `update_id` into `{title, kb_article_ids, severity, categories, deviceIds[], status}`, left-joined against `patch_approvals`. `PATCH /:updateId` (technician) upserts `patch_approvals` via the established check-then-insert-or-update pattern (not `ON CONFLICT`) — `status: 'pending'` deletes the row rather than storing a third status value.
- `PatchesPage.vue` (`/global/patches`) — list page mirroring `GlobalAlertsPage.vue`'s table shape: Title, KB(s), Severity, Categories, Device count, Status pill, Approve/Ignore/Reset actions. Sidebar: "Patches" added to the **Global** section alongside Alerts/Policies/Maintenance Policies/Patch Policies.
- `DeviceDetailPage.vue`'s existing Patches section gained a small read-only status badge per row (fetches the same fleet-wide list alongside everything else in `onIdChange`'s `Promise.all`) — same "summary here, real edit surface is the Global page" pattern the Policies section already establishes on this page.

### Install capability
Approving a patch only ever changed a status, never touched a device — this is the piece that actually does something.

- **Agent**: new `agent/internal/wuinstall` package (`Install(updateIDs []string) Result`) — Windows-only, mirrors `filesize`/`pingutil`/`procutil`/`svcutil`'s small-standalone-package shape rather than living inside `internal/audit` (this is a command, not part of the periodic audit). Re-searches WUA (no find-by-ID lookup exists), filters into a fresh `Microsoft.Update.UpdateColl` by the requested `UpdateID`s, then `CreateUpdateDownloader().Download()` → `CreateUpdateInstaller().Install()` (`AllowSourcePrompts = $false`, defensive — the agent is headless with no interactive session to prompt in anyway). Reports per-update success/failure (`GetUpdateResult(i)`) plus an aggregate `RebootRequired` bool. A 15-minute timeout, well past `collectPatches`'s 180s — downloading+installing a batch can take minutes. `update_ids` are regex-validated as real GUIDs before ever reaching the shelled-out script — defense in depth, not just trusting the caller. No elevation gotcha: the agent already runs as `SYSTEM` (`install_windows.go`'s `mgr.CreateService`, no `ServiceStartName` override), and WUA install is designed to run fully unattended from exactly that context — the same mechanism WSUS/SCCM/Datto's own agent all use.
- **Command dispatch**: new `install_patches` command type (`agent/cmd/agent/main.go`), same one-shot shape as `force_update`/`run_audit` — not the recurring assign-measure-report pattern used by monitor checks, since this is a single user-triggered action. Payload `{update_ids}`; the structured `wuinstall.Result` (per-update outcomes + `reboot_required`) is JSON-encoded straight into the existing `CommandResult.Stdout` field rather than adding a new protocol field or a new `pending_*_results` channel — keeps the wire format untouched, reuses the exact reporting path every other command already has.
- **Worker**: `POST /v1/admin/devices/:id/commands`'s `install_patches` branch **re-validates server-side that every requested `update_id` actually has `status='approved'` in `patch_approvals`** before dispatch, silently dropping any that don't — the dashboard only ever offers approved ones, but this is a real, consequential action on a live machine, worth defense in depth beyond trusting the UI alone. 400s if zero survive the check.
- **Dashboard**: `DeviceDetailPage.vue`'s kebab menu gains "Install Approved Patches (N)" — only rendered when this device has at least one patch that's both currently pending (per its latest audit) *and* fleet-approved (cross-referencing the same `patchApprovalMap` the read-only badge already uses). Bundles everything eligible into one command (one WUA install batch, not one command per patch). Fire-and-forget "queued" toast, same as `restart_agent`/`force_update` — no dashboard polls a direct device command's result today; the device's Patches section naturally reflects success on its next audit anyway, since a successfully-installed update stops appearing in WUA's search.
- **Reboot handling researched directly against Datto RMM** (the actual reference product, not assumed): Datto's real Patch Policy reboot setting is Restart / Shut down / Do not restart (default), where "Do not restart" additionally supports an end-user notification with up to 99 postponable reminders. At the time install capability was built, Beacon's agent had no user-impersonation path (same gap as Components/Job System's declined "run as a logged in user"), so the notification/postpone mechanic was a hard no. That underlying primitive exists now (`agent/internal/usersession`) and a reboot-prompt UI built on top of it shipped too (see Step 1-3 tray notification work in Architecture below) — a manually-triggered install with `reboot_required` always gets the interactive Restart Now/Postpone prompt today. Patch Policy's own `auto_reboot` toggle (below) is the more aggressive opt-in on top of that default.

### Patch Policy (migration `0057`)
Auto-approval rules (originally a `min_severity` MSRC threshold, replaced in a later session — see below) plus scheduled recurring install windows, modeled on Maintenance Policy's targeting/recurrence shape (`maintenance_policies`, `worker/src/lib/maintenance.ts`, migration `0050`) but **not** its runtime model: Maintenance Policy is a passive suppression gate checked on-demand at alert-evaluation time; Patch Policy *actively dispatches* `install_patches` commands at each scheduled window, closer to Jobs' `dispatchDueScheduledJobs` cron-dispatch shape (`worker/src/routes/admin/jobs.ts`) than to Maintenance Policy's `isMaintenanceWindowActive`.

- **Tables**: `patch_policies` — same recurrence columns as `maintenance_policies` (duplicated verbatim, not shared, matching this codebase's established per-policy-type mirroring convention), plus `auto_approve_classifications` (TEXT, JSON array — `[]` means no auto-approval rule, only manually-approved patches ever install; see below for why this replaced a severity threshold), `auto_reboot` (bool, default `false`), and `last_dispatched_at` (nullable INTEGER — see dispatch-tracking below). `patch_policy_companies`/`patch_policy_devices`/`patch_policy_groups` — the exact same 3-table composite-PK OR-list targeting shape as `maintenance_policy_{companies,devices,groups}` (empty = matches every device).
- **Recurrence** (`worker/src/lib/patchPolicies.ts`'s `isPatchWindowActive`) is a verbatim duplicate of `isMaintenanceWindowActive`'s wall-clock/timezone logic, retyped — not shared, same per-policy-type convention as the recurrence columns themselves.
- **Avoiding re-dispatch within one continuous window occurrence**: Jobs' `NOT EXISTS (SELECT 1 FROM commands WHERE job_id = j.id)` trick is one-shot-only and doesn't generalize to a *recurring* weekly window. Instead: dispatch when `isPatchWindowActive(now)` is true **and** (`last_dispatched_at IS NULL OR now > last_dispatched_at + windowDurationSeconds`) — a continuous active stretch can't outlast its own configured duration, so this can't double-fire within one occurrence, and re-arms correctly once the window goes inactive and later recurs.
- **Auto-approval is fleet-wide, same as manual approval** — `patch_approvals` has no per-device concept, so a policy's classification set, matched by any patch present on any device anywhere in the fleet, triggers global approval of that patch (`autoApprovePatches`, reusing `PATCH /v1/admin/patches/:updateId`'s exact check-then-insert upsert shape, not `onConflictDoNothing` — no upsert precedent for that exists elsewhere in this codebase). The policy's own targeting only controls which devices actually *receive* the resulting install, not which patches get approved.
- **Auto-Approval redesigned from an MSRC severity threshold to Windows Update's real Classification taxonomy (migration `0066`, added in a later session from a real "that's not how Windows categorizes its updates" correction)**. Confirmed against Microsoft's own WSUS Classification GUID docs: Windows organizes updates by **Classification** (Critical Updates, Security Updates, Update Rollups, Feature Packs, Service Packs, Tools, Updates, Definition Updates — this last one already filtered client-side before storage, see `agent/internal/audit/patches.go`), and MSRC Severity (Critical/Important/Moderate/Low — the old `min_severity` model) is only meaningfully populated for the Security Updates classification specifically. Every other classification came back `severity: "Unspecified"`, which ranked below even "Low" — meaning Update Rollups, Feature Packs, Service Packs, Tools, and the separate "Critical Updates" classification could **never** auto-approve under any severity threshold, including the most permissive one, a real functional gap not just a labeling mismatch. `patch_policies.auto_approve_classifications` (TEXT, JSON array of `AUTO_APPROVE_CLASSIFICATIONS` — the 7 names above minus Definition Updates) replaces `min_severity` outright (confirmed via AskUserQuestion — replace, not layer a severity refinement alongside; per-patch severity stays a **display-only** field on the Patches page, unaffected). `autoApprovePatches` now checks `patch.categories.some(c => classifications.includes(c))` — `FleetPatchState` gained a `categories: string[]` field (the agent already collected this, previously only used to filter out Definition Updates) so this needed no new agent-side data. Dashboard: `PatchPolicyFormPage.vue`'s Auto-Approval `<select>` became a pill-checkbox multi-select (same shape as the Class section next to it); `PatchPoliciesPage.vue`'s Auto-Approve column shows `Off` / the classification name(s) / `"N classifications"` once more than 2 are selected (110px column, joining all 7 would overflow). Verified live against local `wrangler dev`: seeded a real pending patch with `severity: "Unspecified"`, `categories: ["Update Rollups"]` — a policy auto-approving only "Security Updates" correctly left it pending; adding "Update Rollups" to the same policy correctly auto-approved it on the next cron tick, proving the exact gap is closed, not just the code path exercised. **`AUTO_APPROVE_CLASSIFICATIONS` was further trimmed to just 2 values, `Security Updates` + `Update Rollups`** (PR #64, same session) — the other 5 (Critical Updates, Feature Packs, Service Packs, Tools, plain "Updates") are all effectively obsolete on any Windows 10 1903+/current Server device (Microsoft stopped populating Critical Updates in 1903, consolidating almost everything into Security Updates; Feature Packs/Service Packs predate the Windows-as-a-service model). **Real bug found and fixed in a later session**: `PatchPolicyFormPage.vue`'s edit-load path (`onIdChange`) parsed a policy's stored `auto_approve_classifications` straight into the form with no filtering — a policy saved before this trim (with one of the 5 now-removed values still selected) loaded fine (the removed pill just isn't rendered, so nothing looked wrong), but re-saving it re-sent the stale value verbatim and the server's `validateAutoApproveClassifications` correctly 400'd it (`must be an array of: Security Updates, Update Rollups`) — hit live on a real policy, disproving PR #64's own commit-message claim that "production's only real policy already has an empty array." Fixed by filtering the parsed array against the current `AUTO_APPROVE_CLASSIFICATIONS` at load time — silently dropping a classification that's already been established as never-occurring-in-real-data is the correct behavior here, not a data-loss risk.
- **Dispatch** (`dispatchDuePatchPolicies`, called from `worker/src/index.ts`'s `scheduled()` cron alongside the existing three calls): runs `autoApprovePatches` first, then for each due policy resolves targeted devices via `deviceMatchesPatchPolicy` (exact mirror of `deviceMatchesMaintenancePolicy`'s OR-list check), intersects each device's currently-pending `update_id`s against globally-approved ones, and inserts one `commands` row directly per eligible device (`type: 'install_patches'`, `payload: {update_ids, auto_reboot: policy.autoReboot}`) — bypassing the per-device HTTP route and `insertJobCommands` entirely, matching how Jobs' own scheduled dispatch inserts directly too.
- **`auto_reboot` payload extension**: the manual per-device `POST /v1/admin/devices/:id/commands` route never sends `auto_reboot` (always falls through to the interactive tray prompt); only a Patch Policy dispatch sets it. `agent/cmd/agent/main.go`'s `install_patches` handler branches on it — `true` + `RebootRequired` skips `writePendingRebootMarker()` and runs `shutdown /r /t 0` directly instead.
- **Worker routes** (`worker/src/routes/admin/patch-policies.ts`, mounted at `/v1/admin/patch-policies`) mirror `maintenance-policies.ts`'s exact route list and role tiers (`readonly` GET, `technician` mutate): `GET/POST /`, `PATCH/DELETE /:id`, nested `GET/POST /:id/companies|devices|groups` + `DELETE .../:targetId`. `clone_from` on `POST /` also copies `min_severity`/`auto_reboot` and calls `copyPatchPolicyTargets`.
- **Dashboard**: `PatchPoliciesPage.vue`/`PatchPolicyFormPage.vue` (`/global/patch-policies`, `/global/patch-policies/new`, `/global/patch-policies/:id`) mirror `MaintenancePoliciesPage.vue`/`MaintenancePolicyFormPage.vue` exactly (same Targets flyout, same seg-bar schedule picker), plus two sections Maintenance Policy doesn't have: **Auto-Approval** (Windows Update Classification pill-checkboxes, see below) and **Auto Reboot** (Disabled/Enabled seg-bar, defaulting Disabled). Sidebar: "Patch Policies" link in the **Global** section, after Patches.
- **Device Class targeting** (migration `0064`, added in a later session from a real "I need to target workstations only" ask) — `patch_policies.target_class` (JSON array TEXT, default `'["server","workstation","laptop"]'`), same convention as `policies.targetClass`. **No OS dimension** — unlike regular Policies' "OS & Class" section, Patch Policy deliberately only got Class: Patch Management already only ever runs against Windows devices, so an OS filter here would be permanently inert. ANDed with the Company/Device/Group OR-list in `deviceMatchesPatchPolicy` (class check first, short-circuits before the OR-list) — this function is shared with `windowsUpdateManagement.ts`'s own coverage check, so a class-scoped Patch Policy correctly excludes out-of-class devices from Windows Update Management takeover too, with no extra code needed there. Dashboard: a "Class" section (pill checkboxes, no OS row) on `PatchPolicyFormPage.vue` between Schedule and Targets — same ordering as regular Policies' OS & Class-before-Targets. `PatchPoliciesPage.vue`'s Targets column folds a non-default class selection into its existing summary (`"Workstation · All devices"`), same `·`-separated convention `GlobalPoliciesPage.vue`'s own OS/Class summary already uses.
- **Explicitly out of scope**: anything beyond a single severity-threshold rule (no category/KB-pattern filter builder), Datto's finer-grained *per-policy* per-target enable/disable overrides (a company-wide blanket exclusion exists instead, see below), patch rollback/uninstall on failure, per-update retry logic, any Shared Dashboards widget.
- **Company-level exclusion + Patch Policy "Override" (migration `0065`, added in a later session)** — came up from the user's own real Datto RMM usage pattern: a global policy covering the fleet, with per-company overrides (company-scoped copies) for companies that need different handling. That model doesn't actually work with Beacon's pure OR-list targeting on its own — an unrestricted global policy (zero targets) matches *every* device by default, so creating a company-scoped override alongside it doesn't stop the global policy from also applying; nothing previously let a company opt out of a match at all. Confirmed via AskUserQuestion: a **company-wide blanket flag** (`companies.patch_management_excluded`, bool, default `false`), not Datto's finer per-policy exclusion list — for a company managing Windows Update its own way (WSUS, etc.) that shouldn't have any Beacon Patch Policy forced onto it. Checked first, unconditionally, inside `deviceMatchesPatchPolicy` (`worker/src/lib/patchPolicies.ts`) via a new `fetchExcludedCompanyIds()` helper (same fetch-once-per-invocation convention as every other `fetchPatchPolicy*Ids` helper) — short-circuits `false` before the Class/Company/Device/Group checks, so no per-policy exception is possible, by design. Since `windowsUpdateManagement.ts`'s `syncWindowsUpdateManagement` already calls this same function for its own coverage check, the same flag automatically excludes a company from AU takeover too, with zero extra code — confirmed live via a real dispatch cycle against local `wrangler dev` (excluded → `{action:'revert'}`, un-excluded → `{action:'manage'}`, same policy, same device, only the flag changed). Dashboard: a new "Exclude from Patch Policies" toggle in `CompaniesPage.vue`'s Create/Edit modal (`Settings` section, alongside Auto-approve/Privacy mode default) plus a small `badge-revoked` "No Patch Mgmt" tag next to the company name in the list when set. `PatchPoliciesPage.vue` also gained the same one-click "Override" button + "Create Company Override" modal `GlobalPoliciesPage.vue` already has (clone selected polic{y,ies} via `clone_from`, then add the chosen company as a Target) — CSS duplicated locally per this codebase's convention, since Patch Policy's flat list (no global/company tab split, no derived `scope` column) has no basis for `GlobalPoliciesPage.vue`'s own "only global policies can be overridden" restriction, so it's allowed for any selection.
- **Real-hardware verification**: the underlying `usersession.RunAsSession` mechanism (shared with Job execution's "run as a logged in user", see below) was confirmed working on real hardware. `wuinstall.Install()`'s actual WUA download+install path and the `auto_reboot` direct-shutdown branch specifically were **not cleanly confirmed** — every real attempt hung at `IUpdateDownloader.Download()` on the one available test machine, reproduced with a hand-written PowerShell script that never touches Beacon's code at all, so the hang is provably not caused by anything in this codebase (BITS was confirmed running, WUA search/match worked fine — the download itself just never progressed, cause unknown). The `auto_reboot` conditional (`agent/cmd/agent/main.go`) was therefore never actually reached in a real run; shipped on code review given how small and low-risk it is (a single boolean-gated call to the same `shutdown` invocation the existing `reboot` command already uses in production).

### Managing Windows' own Automatic Updates (migration `0063`)
The rest of Patch Management drives Windows Update entirely through the native WUA COM API (`agent/internal/wuinstall`) — but Windows has a *separate* "Automatic Updates" client (governed by the AU Group Policy registry keys under `HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU`) that Beacon never touched before this. Left enabled, that client can install an update Beacon hasn't approved, or reboot outside a configured Patch Policy window — quietly defeating the whole point of the approval/scheduling workflow. Came up mid-session discussing Patch Management's design; confirmed via AskUserQuestion: Beacon should actively take this over (standard behavior for a real RMM agent), **opt-in per Patch Policy** (not automatic for every policy-covered device — matches this codebase's consistent "explicit opt-in, never a retroactive default flip" convention, same as `auto_reboot` itself), and **no drift detection in v1** (no continuous re-check that a domain GPO hasn't silently re-enabled it later — deferred to Icebox, matching this session's Network Discovery scope-down).

The one hard safety requirement: **never leave a device with Windows Update disabled and no Beacon coverage to actually patch it** — solved by tying takeover strictly to real, freshly-recomputed Patch Policy coverage every cron tick (the same "recompute targeting from scratch, never incrementally" rule `dispatchDuePatchPolicies` already follows) and reverting the instant coverage is lost for *any* reason — toggle turned off, policy disabled/deleted, device retargeted. There's no special-case code for any of those triggers; they're all just "coverage recomputed differently this tick."

- **`patch_policies.manage_windows_update`** (bool, default `false`) — the opt-in toggle.
- **`devices.windows_update_managed`** (nullable bool — `NULL` means never evaluated, e.g. non-Windows or not yet covered), **`devices.windows_update_prior_state`** (nullable JSON snapshot of the AU registry values from immediately before Beacon's *first* takeover — used to revert to the device's real prior configuration, not a guessed default), **`devices.windows_update_managed_at`** (nullable, for the dashboard's "since ..." display). Columns land directly on `devices`, not a new joined table — matches how `maintenanceEndsAt`/`maintenanceReason`/`warrantyExpiresAt` already model similar 1:1 per-device state.
- **`syncWindowsUpdateManagement`** (`worker/src/lib/windowsUpdateManagement.ts`, called from `scheduled()` alongside `dispatchDuePatchPolicies`) — for every approved Windows device, computes desired state via `deviceMatchesPatchPolicy` against only the enabled policies with `manage_windows_update=true`, **evaluated independent of window-active state** (gating on `isPatchWindowActive` would defeat the entire point of pre-emptively disabling auto-update *ahead of* a scheduled window that hasn't opened yet — coverage is about whether a qualifying policy exists at all). `fetchEnabledPatchPolicies`/`fetchPatchPolicy{Company,Device,Group}Ids`/`deviceMatchesPatchPolicy` were exported from `patchPolicies.ts` specifically for this reuse. On a mismatch against `devices.windowsUpdateManaged`, and only if there's no already-outstanding (`queued`/`sent`) `manage_windows_update` command for the device (same guard Jobs already uses to avoid redispatch pile-up on an offline device), inserts one `commands` row — `{action:'manage'}` or `{action:'revert', prior_state: <stored snapshot>}`.
- **Dispatched through `commands`, deliberately not the check-in wire protocol** — a direct, deliberate lesson from a real production incident this same session, where renaming a `CheckInRequest`/`EnrollResponse` wire field broke check-in fleet-wide (see `worker/src/lib/types.ts`'s `EnrollResponse`/`CheckInRequest` comments, and PROJECT_LOG.md's "2026-07-31 / 2026-08-01" entry for the full incident writeup): extending the check-in wire protocol is exactly the wrong surface to add new functionality to when a config-driven, cron-to-one-device dispatch model (which Patch Policy's own `install_patches` dispatch, and Network Discovery's `network_scan`, both already prove out) does the job with zero shared wire-type changes.
- **Agent** (`agent/internal/auconfig`, new package) — `Apply(action, priorNoAutoUpdate, priorAUOptions) Result` shells out to PowerShell (`Get-ItemProperty`/`Set-ItemProperty`/`Remove-ItemProperty`) rather than the native `x/sys/windows/registry` package — confirmed via direct grep that **no existing code in this agent uses that package**; every other Windows-specific read/write, including WUA itself, already shells out to PowerShell, so this matches established convention rather than introducing a new one. `action:"manage"` sets `NoAutoUpdate=1` (takes Windows' own Automatic Updates client fully offline — Beacon's own WUA-driven install doesn't need it running at all); `action:"revert"` restores the caller-supplied prior values, **removing** a registry value that didn't exist before rather than guessing a default. Both branches read-then-report the pre-write snapshot regardless of action, using the same two-struct PascalCase-PS-output/snake_case-wire-`Result` pattern `wuinstall` already established. New `manage_windows_update` command branch in `agent/cmd/agent/main.go`, same shape as `install_patches`/`network_scan` — no protocol type changes needed anywhere, the payload/result both ride the existing generic `Payload`/`Stdout` fields.
- **Dashboard**: `PatchPolicyFormPage.vue` gained a "Manage Windows' own Automatic Updates" seg-bar toggle (Disabled/Enabled, default Disabled), same section-group placement and markup as Auto Reboot. `DeviceDetailPage.vue`'s Patches section gained an always-visible status row — "Managed by Beacon" (`inv-badge-ok`) / "Not managed" (`inv-badge-muted`), with a "since {date}" suffix when managed — sourced directly from the device row (`windowsUpdateManaged`/`windowsUpdateManagedAt`), not audit data, since the worker (not the agent) is the one that actually knows/commands the desired state.
- **Explicitly out of scope (Icebox)**: drift detection (no continuous re-check that a domain GPO or manual admin action hasn't silently re-enabled Windows' own Automatic Updates after Beacon disabled it — v1 dispatches and records success/failure only); automatic-for-all-covered-devices (deliberately opt-in per policy instead).
- **Not verified on real hardware** — same environment limitation as the rest of this session's Windows-specific work; no live Windows box available. The PowerShell script-rendering logic (null-vs-zero-vs-integer literal handling for the revert path, the non-Windows early-return guard) was verified via a throwaway Go test, but the actual registry read/write against a real `HKLM` hive was not.

### Drivers + Microsoft Update (migration `0067`, added in a later session)
Two more Patch Policy capabilities, both surfaced from a real "why doesn't this cover X" question rather than pre-planned scope:

- **Drivers** — originally excluded entirely (`Type='Software'` in the WUA search criteria) as "noisy," an unconfirmed call from an earlier session, corrected once actually questioned: "who made this decision?" turned up that it was never actually confirmed with the user. Now a per-Patch-Policy opt-in (`patch_policies.include_drivers`, bool, default `false`) — **visibility + manual-approval only, never Auto-Approval-eligible, confirmed via AskUserQuestion** (a bad driver can break hardware/boot in a way a bad software patch usually can't). The agent's WUA search criteria dropped `Type='Software'` entirely (now scans both types unconditionally) and tags each item's own `Type` (`agent/internal/audit/patches.go`) — **WUA's `IUpdate.Type` is a raw enum integer (1=Software, 2=Driver), not a string**, confirmed via research before writing agent code that runs as SYSTEM on real machines; the PowerShell script converts it to a friendly name itself, matching how `Categories`/`MsrcSeverity` already are. Rather than thread per-device coverage into the check-in wire protocol or build new agent-side persisted config (both deliberately avoided), the opt-in is enforced as a **storage-time filter** in `worker/src/routes/audit.ts` (`deviceHasDriverVisibility`) — mirrors the *existing* privacy-mode software/services-stripping precedent in that exact file, not a new mechanism. `autoApprovePatches` (`worker/src/lib/patchPolicies.ts`) additionally, explicitly skips any `type === 'driver'` patch regardless of category match — Category and Type are independent WUA properties, so a driver update's own categories could in principle overlap a classification rule without this being a hard, non-incidental guarantee. Verified live against local `wrangler dev`: submitted a real `/v1/audit` request via a device's actual credential with both a software and driver patch — driver item correctly stripped with no covering policy, correctly kept once one existed; a synthetic worst-case driver update sharing a "Security Updates" category with an active Auto-Approval rule stayed `pending`, confirming the explicit skip actually holds. Dashboard: `PatchesPage.vue`/`DeviceDetailPage.vue`'s Patches section both gained a small `badge-pending` "Driver" tag, shown only for driver-type items (software stays unbadged — the overwhelmingly common case).
- **Microsoft Update** — the separate "Microsoft Update" service registration (`Settings > Windows Update > Advanced options > "Receive updates for other Microsoft products..."`) that broadens WUA's search to include Office/other Microsoft product updates, not just the OS. Left to a device's out-of-box default, a technician relying on Beacon for patch coverage would have no idea whether this was ever turned on — same shape of problem `manage_windows_update`/`auconfig` already solved for the AU client. **Independent toggle, not folded into `manage_windows_update`** (confirmed via AskUserQuestion — matches this codebase's existing convention of `auto_reboot`/`manage_windows_update` themselves being separate, not one blanket flag). New `agent/internal/muconfig` package, a structural mirror of `auconfig` (manage/revert-with-prior-state-snapshot, same two-struct PascalCase-PS-output/snake_case-wire-`Result` pattern) but driving `Microsoft.Update.ServiceManager`'s `AddService2`/`RemoveService` COM methods against the well-known Microsoft Update service GUID (`7971f918-a847-4430-9279-4a52d1efe18d`) rather than a registry key — confirmed via research (working example code, not guessed) since no single well-documented registry value covers this specific opt-in the way `auconfig`'s AU registry key does. `worker/src/lib/microsoftUpdateManagement.ts`'s `syncMicrosoftUpdateManagement` is a verbatim structural mirror of `syncWindowsUpdateManagement` (own command type `manage_microsoft_update`, own `devices.microsoftUpdateManaged`/`microsoftUpdatePriorState`/`microsoftUpdateManagedAt` columns, same outstanding-command guard, same coverage-lost-for-any-reason-reverts-next-tick safety property) — not shared code, matching this session's own established per-capability mirroring convention. Verified live: flipping the policy toggle and clearing a stale outstanding command from an earlier, unrelated test produced the expected `{"action":"manage"}` dispatch. Dashboard: `PatchPolicyFormPage.vue` gained a "Manage Microsoft Update" seg-bar (identical shape to "Manage Windows' own Automatic Updates," placed directly below it), `DeviceDetailPage.vue`'s Patches section gained a second "Managed by Beacon"/"Not managed" status row.
- **Not verified on real hardware** — same environment limitation as the rest of this feature area. The COM `AddService2`/`RemoveService` calls and the widened driver search criteria were verified against real Microsoft documentation/example code and via the local `wrangler dev` pipeline described above, but never against a real Windows `Microsoft.Update.ServiceManager` COM object.

### Class simplified to Server/Client OS + automatic Hyper-V host exclusion (migration `0068`, added in a later session)

Prompted directly by the user's own 25+ years of real patch-management experience: `patch_policies.target_class`'s three checkboxes (Server/Workstation/Laptop) don't map to how patching decisions actually get made. Confirmed by reading `agent/internal/inventory/collect.go`'s `detectClass()` before assuming anything: Workstation vs. Laptop is decided *purely* by battery presence (`hasBatteryWindows()`/`hasBattery()`) — a hardware form-factor signal with zero patch-management relevance. Separately, "server" as a single bucket is too coarse in the other direction: a Hyper-V host needs categorically different handling than an ordinary server (a bad reboot takes every VM on it down, not just itself) — the user's own words: "I've never seen in 25+ years where a client wants to automatically patch and restart the hyperv host... normally it's manual because they have to verify it's clustered or in maintenance mode, migrate VMs off, or they can down production servers on it."

**Scope, confirmed via AskUserQuestion before building**: Patch-Policy-only, not a `devices.class` schema change — `detectedClass`/`overrideClass` stay exactly `server`/`workstation`/`laptop` everywhere else (Device Groups, Network Discovery's laptop exclusion, general device filtering all untouched). `PatchPolicyFormPage.vue`'s Class section shows two pills, **Server** / **Client OS** — each pill toggles its full underlying value set (`['workstation','laptop']` for Client OS) together in `form.targetClass`, a pure dashboard presentation change with no backend contract change (the stored array shape, and `worker/src/routes/admin/patch-policies.ts`'s `VALID_CLASSES` validation, are both unchanged). `PatchPoliciesPage.vue`'s list summary mirrors the same two-bucket labeling, with a fallback to the old per-value listing for any legacy policy stuck in a partial state from before this merge (e.g. only `workstation` checked, never `laptop`).

**Hyper-V host exclusion has no opt-out toggle, confirmed via AskUserQuestion** — the only way to patch a Hyper-V host through Beacon is a policy that explicitly Device- or Group-targets it, which is a deliberate, one-off, manually-curated action matching how the user described actually doing this in practice; company-wide targeting does **not** bypass the exclusion, since it's just as much an unattended sweep as the class-based default.

- **Detection**: new `agent/internal/audit/hyperv.go`, `collectHyperVHost()` — Windows-only, checks for the `vmms` (Virtual Machine Management Service) service via `Get-Service -Name vmms -ErrorAction SilentlyContinue`, the standard signal for both the Server Hyper-V role and the client Hyper-V Platform optional feature (presence, not running-state, is what matters). Returns `nil` (not `false`) on non-Windows or any collection failure — kept distinct from a confirmed non-host so a transient PowerShell failure can never un-exclude a real host. Rides the existing audit flow (`AuditPayload.HypervisorHost *bool`, `omitempty`) rather than the check-in wire protocol — this is a slow-changing hardware/role fact, not something that needs 60s-cadence freshness, matching `collectPatches()`'s own cadence reasoning.
- **Storage**: `devices.is_hyper_v_host` (nullable bool, `NULL` = never evaluated) — a real column, not folded into the JSON audit blob, since `deviceMatchesPatchPolicy` needs to check it on every cron tick across the whole fleet without per-device JSON parsing. `worker/src/routes/audit.ts`'s ingest handler only touches this column when the agent's payload actually includes the key (`payload.hypervisor_host !== undefined`) — a non-Windows device or one transient collection failure never overwrites a previously-known value with a false negative.
- **Matching logic** (`worker/src/lib/patchPolicies.ts`'s `deviceMatchesPatchPolicy`): the Hyper-V check now runs *before* the class check, computing `matchesDevice`/`matchesGroup` first so it can gate on them — `if (device.isHyperVHost && !matchesDevice && !matchesGroup) return false`. Explicit Company-list membership deliberately does **not** count toward the bypass (only Device/Group do), consistent with the "company targeting is a sweep, not a curated selection" reasoning above. Since `windowsUpdateManagement.ts`/`microsoftUpdateManagement.ts`/`deviceHasDriverVisibility` all already reuse this exact function for their own coverage checks, the same exclusion (and the same explicit-targeting bypass) applies to AU/Microsoft-Update takeover and driver visibility automatically, with zero extra code — the identical "for free" pattern the company-exclusion flag and Device Class targeting already established.
- **Dashboard visibility**: `DeviceDetailPage.vue`'s Patches section gained a "Hyper-V Host" status row (only rendered when `isHyperVHost != null`, i.e. actually evaluated) — deliberately added even though not explicitly asked for, since a silent, undiscoverable exclusion would just generate "why isn't Beacon patching this server" support confusion later, the same reasoning behind every other "Managed by Beacon"/"Not managed" badge in this section.
- **Verified live end-to-end against local `wrangler dev` + real D1** (agent-side Go code couldn't be compile-checked at all in this session's sandbox — no Go toolchain available — so this was verified purely through direct D1 seeding + the real dispatch cron, not through an actual agent): seeded a `server`-class device with `is_hyper_v_host=1` and a plain `server`-class device with `is_hyper_v_host=0`, created a real Patch Policy with `manage_windows_update` enabled and an unrestricted Server-class target, triggered the cron — the plain server correctly got `{"action":"manage"}` dispatched, the Hyper-V host got nothing (no coverage, matching the "revert" default). Then explicitly Device-targeted the Hyper-V host on the same policy and re-triggered (after clearing a stale queued command that was blocking re-evaluation via the existing outstanding-command guard) — it then correctly received `{"action":"manage"}` too, confirming the explicit-targeting bypass actually works, not just compiles.
- **Not verified on real hardware** — same environment limitation as the rest of this feature area; the `vmms`-service-presence detection itself has not been confirmed against a real Hyper-V host or a real Windows client with the Hyper-V feature enabled.

## Remote Agent Uninstall

`uninstall_agent` command type (`agent/cmd/agent/main.go`, dispatched via the existing `POST /v1/admin/devices/:id/commands`) — added directly from real hardware-testing pain this session, originally motivated by the tamper-resistance hardening (`hardenService`'s SDDL + `hardenInstallDir`'s ACL) locking a running agent down to SYSTEM-only stop/delete/write, leaving no way for an external admin to reinstall or remove it without local registry surgery + a reboot. **That hardening has since been removed** (see Architecture above / `setRecoveryActions`' doc comment) — but this command remains genuinely useful on its own as a remote-uninstall convenience even without that original ACL-fight motivation, so it stayed. The *already-running* SYSTEM-context service tears itself down on request rather than requiring an external caller to do it.

- **`service.SelfUninstall()`** (Windows: `install_windows.go`; Linux/macOS: `install_unix.go`) is deliberately **not** a reuse of the existing `Uninstall()` (invoked by a separate, one-shot `beacon-agent.exe uninstall` process). Calling `Uninstall()`'s synchronous Stop-then-Delete-then-Remove sequence *from inside the process being torn down* would race its own termination: on Windows, `s.Control(svc.Stop)` asks SCM to deliver a stop request back to this exact process's own `Execute()` loop, and once actioned the process is expected to exit — but the goroutine that called Stop is a detached child of the check-in loop, not awaited by it, so the whole process could be torn down before `Delete()`/`os.Remove()` ever run. On Linux/macOS, `systemctl stop`/`launchctl unload` block until the unit actually exits, and since neither the agent nor Go installs a custom SIGTERM handler, the OS's default SIGTERM action (immediate termination) fires the moment the stop takes effect, killing the process mid-call. Same fix on both platforms: **disable recovery/restart first** (Windows: `SetRecoveryActions(nil,0)` + `SetRecoveryActionsOnNonCrashFailures(false)`, since `setRecoveryActions` configures SCM to resurrect the service on *any* exit including a clean one — skipping this would let SCM restart the "crashed" service before cleanup finishes), then **spawn a small detached helper** (`cmd.exe`/`sh -c`, `.Start()` not `.Run()`) that performs the actual stop+delete+remove after a few seconds' delay — long enough for this process to have fully exited and released its own file handle and SCM connection — then let this process exit normally. A child process's lifetime isn't tied to its parent's on any of these platforms, so the helper survives.
- **No result is ever reported back** for this command, same fire-and-forget shape as `restart_agent` — the device going quiet in check-ins entirely is the only confirmation this ever produces; there's no later check-in to report success/failure on.
- **Dashboard**: `DeviceDetailPage.vue`'s kebab menu gains "Uninstall Agent" (danger-styled, next to but distinct from the pre-existing "Delete Device") with a `confirm()` dialog (this codebase's established destructive-action pattern) spelling out that it only removes the *remote agent install*, not Beacon's own device record/history — the device just goes offline rather than disappearing from the dashboard, unlike "Delete Device."
- **Real-hardware verification, three real bugs found, all fixed**: dispatched against a real Windows box, the service and its registry entry both cleanly disappeared, but `C:\Program Files\Beacon` was left behind with the tray icon still visibly running. Root cause: `beacon-tray.exe` runs as a *separate* process launched into the logged-in user's own session (`usersession.RunAsSession`), not a child of the service being stopped — its own open file handle on `beacon-tray.exe` blocks `rd /s /q`. Fixed with `taskkill /IM beacon-tray.exe /F` in the helper script (SYSTEM's `SeDebugPrivilege` reaches a process in a different session; `/IM` catches every instance across every session, covering RDS/multi-session too). **Retested after that fix and the directory was still left behind** — a second cause: the helper's `timeout /t 3` step needs a real console input handle even with `/nobreak`, and this helper runs with `CREATE_NO_WINDOW` from a SYSTEM service with no console at all, so `timeout` failed immediately, collapsing the intended delay to zero and racing `rd /s /q` against this process's own in-progress exit. Switched to `ping -n 4 127.0.0.1 >nul` (the standard no-console-needed batch-scripting delay idiom). **Retested again and both `installDir` and `credential.Dir()` were still left behind completely untouched, not just one locked file within each** — a third cause, this time correctly diagnosed from that exact symptom: `cmd.exe`'s `rd /s /q` aborts its *entire* recursive delete the instant it hits one locked file (this process's own loaded image inside `installDir`, its own open log file inside `credential.Dir()`) rather than skipping it and continuing the way Explorer's delete does — so a merely-too-short fixed delay doesn't leave partial cleanup behind, it leaves *no* cleanup at all. Fixed by replacing the guessed fixed delay with an active wait on the condition that actually matters: the helper (rewritten in PowerShell) calls `Wait-Process -Id <this process's own PID> -Timeout 30` before touching either directory, then uses `Remove-Item -Recurse -Force` (more forgiving of a single locked file within a tree than `rd /s /q`) with each removal's real success/failure logged to `C:\Windows\Temp\beacon-uninstall.log` — a location outside both directories being removed, so evidence survives even if a removal fails again. **Verified on real hardware** (agent v0.2.17) — `C:\Program Files\Beacon` and `C:\ProgramData\Beacon` both fully removed after "Uninstall Agent," confirmed via `verify-uninstall.ps1`. The self-referential stop/restart race the design was originally built to avoid was never actually hit live — all three real bugs found were simpler oversights (an unrelated process holding a lock; a delay primitive that doesn't work in a headless context; a guessed delay racing real file locks), the kind only real hardware turns up.
- **A third real gap found in a later session, from the same real-hardware reinstall cycle**: `credential.Dir()` (`%PROGRAMDATA%\Beacon` on Windows, `/etc/beacon` on Linux, `/Library/Application Support/Beacon` on macOS — holding `credential.json` and `agent.log`) is a **separate location from `installDir`/the platform bin path** and was never touched by *any* uninstall path on *any* platform (`Uninstall()`/`uninstallLinux()`/`uninstallDarwin()`, and both platforms' `SelfUninstall()`). A stale `credential.json` left behind meant a later reinstall silently loaded the old credential and skipped re-enrollment entirely, rather than registering as a fresh device — exactly what happened during this session's own STCSLT001 reinstall testing, and the direct trigger for this fix. Every uninstall path on every platform now also removes `credential.Dir()` (`os.RemoveAll`, best-effort, same as the rest of each function). Windows' `Uninstall()` additionally gained the same `taskkill /IM beacon-tray.exe /F` + whole-`installDir`-removal `SelfUninstall()` already had (it previously only did a bare `os.Remove(installPath())`, i.e. just the one exe, leaving the tray binary and everything else behind) — the plain CLI-invoked `uninstall` command is a separate process from the service being removed, so no detached-helper/self-termination-race concern applies there; it can kill the tray and remove the directory directly and synchronously.

## Activity Log

Master audit log — accountability ("who did what") + fleet-wide operational visibility, built after researching Datto RMM's real Activity Log (account-wide, filterable by company/device/user, no per-company default scope) as the reference. A detour into porting Datto's much larger granular "Security Levels" RBAC model was explicitly tabled first — Beacon's existing 3-tier role system (`admin`/`technician`/`readonly`) stays exactly as-is; this feature is purely a logging layer on top, not an RBAC change.

### Two-layer instrumentation (migration 0058)
So "everything that happens" doesn't depend on remembering to instrument every route by hand:

1. **Layer 1 — generic middleware** (`activityLogMiddleware`, `worker/src/lib/activityLog.ts`), registered in `index.ts` on five mount-prefix families (`/v1/admin/*`, `/v1/auth/*`, `/v1/sessions`+`/v1/sessions/*`, `/v1/branding/*`) **before** the `app.route()` mounts, same ordering `corsMiddleware` already uses for these same prefixes. After a successful (2xx) mutating (POST/PATCH/PUT/DELETE) request, it resolves the actor by calling `requireUser()` a second time (one extra cheap D1 lookup, only on successful mutations) — deliberately **not** reading anything the route handler set via `c.set()`, since `requireUser()` never receives the Hono `Context` at all (every call site passes discrete primitives `authHeader`/`env`), so there's nothing to read. Looks up `(method, c.req.routePath)` — confirmed from Hono source that `routePath` returns the *full* path from the root app even for routes mounted via `app.route()`, e.g. `/v1/admin/jobs/:id`, not a sub-app-relative pattern — in a ~90-entry `FINE_GRAINED` table for a nice human `action` label, falling back to a ~24-entry `PREFIX_DEFAULTS` mount-prefix→`{category, noun}` map for any route not explicitly listed, so a route added later with zero lookup-table entry still gets *something* logged rather than being silently dropped. `entityId` defaults to `c.req.param('id')` generically (`idParam` override only needed for the one route with no `:id` param at all, `/v1/admin/patches/:updateId`). `companyId` is enriched via one extra device lookup, but only for `entityType === 'device'` — most other entity types (policies, jobs, components) can span multiple companies and aren't unambiguously owned by one.
   - **Real bug found and fixed during local verification**: a single request can match more than one registered middleware prefix (e.g. the bare path `/v1/sessions` matches both the exact `/v1/sessions` registration and the `/v1/sessions/*` wildcard — the same double-registration `corsMiddleware` already has for this prefix, harmless there since header-setting is idempotent, but not harmless for a DB insert). Produced a real duplicate row in testing. Fixed with a `c.set('activityLogWritten', true)` guard checked at the top of the middleware, since Hono's `compose()` gives each matching prefix its own layer in the onion chain and both would otherwise run their full post-`next()` body independently.
   - **Must read `c.req.routePath`/`c.req.param()` strictly *after* `await next()`**, not before — confirmed from Hono's `compose.js` source that `routeIndex` (and therefore `routePath`) reflects whichever layer most recently dispatched, so reading it before `next()` would give the middleware's own registration pattern instead of the terminal handler's actual matched route.
   - **Read-only note**: reading `c.req.routePath`/`c.req.param()` after the handler already ran also means a bare `POST` to a collection root (e.g. `POST /v1/admin/companies`) has no `entityId` to log — the new row's real ID only exists in the *response* body, not the request, and this doesn't buffer/parse `c.res` to extract it. A real, deliberate v1 limitation, not a bug.
2. **Layer 2 — a handful of explicit `logActivity()` calls** for mutations that never go through a user-authenticated HTTP route at all: `routes/auth.ts`'s `POST /login` (both the shared `invalid()` failure closure — capturing the attempted email, never the password — and the success path; no `Authorization` header exists yet for Layer 1 to resolve an actor from), `routes/auth-microsoft.ts`'s `GET /callback` right after the `userSessions` insert (the actual SSO login moment; a `GET`, so Layer 1's mutating-method gate wouldn't catch it even if in scope — `POST /exchange` is a mutating route under `/v1/auth/*` that *would* otherwise double-log the same login, so it's in Layer 1's explicit `SKIP_ROUTES` set), `lib/alerts.ts`'s `processAlertState` (three distinct trigger points: immediate-fire, sustained-fire, auto-resolve — kept separate since they're meaningfully different facts, not one generic "alert changed" hook), `routes/admin/jobs.ts`'s `dispatchDueScheduledJobs` (one call per dispatched job — job *creation* is a normal Layer-1-covered admin route), and `lib/patchPolicies.ts` (two separate call sites: `autoApprovePatches` per patch auto-approved, `dispatchDuePatchPolicies` per policy that actually dispatched ≥1 install command).

### Schema
`activity_log` — `id`, `createdAt`, `actorType` (`'user'|'system'|'break-glass'`), `actorId`, `actorLabel` (email/displayName **snapshot** — survives the user being deleted later, same convention `patch_approvals` already established for title/severity), `category`, `action`, `entityType`, `entityId`, `companyId`, `method`, `path` (raw, debugging fallback), `details` (nullable JSON). **Deliberately no FK constraints** on `actorId`/`entityId`/`companyId` — this table must never cascade-delete, or be blocked from writing, just because it recorded something about a row that's since been removed. `entityId` is **not** similarly snapshotted with a friendly name — full per-entity-type name resolution across ~15 different entity tables was scoped out of v1 as real added complexity for a nice-to-have; the dashboard instead renders a cheap, always-correct click-through link (`ENTITY_ROUTES` map in `ActivityLogPage.vue`, ~11 entity types) straight to the real entity page, which shows its own name once you land on it.

### Retention
`pruneActivityLog()` deletes rows older than 180 days, called from `index.ts`'s `scheduled()` cron. Throttled via a new `host_settings.activity_log_pruned_at` column — a **persisted timestamp**, not a stateless tick-bucket check — so a missed/delayed cron tick can't silently skip an entire day's prune; mirrors `userSessions.lastUsedAt`'s own throttle shape.

### Dashboard: the first genuinely unbounded, account-wide-forever table in this codebase
Every other "unbounded" list page (`DeviceChangeLogPage.vue`, `JobsPage.vue`) is actually bounded-by-cap client-side pagination over a server `LIMIT`. `GET /v1/admin/activity-log` does real server-side filtering (`company_id`/`actor_id`/`category`/`entity_type`/`entity_id`/`from`/`to`) + pagination (plain `LIMIT`/`OFFSET` + a matching `COUNT(*)`, not keyset/cursor — this project's self-hosted scale doesn't need keyset's complexity, and `LIMIT`/`OFFSET` lets `ActivityLogPage.vue` (`/global/activity`) reuse the existing numbered `.pagination` bar's UI/interaction unchanged, just fetching per-page from the server on every filter/page change instead of pre-loading everything into a `computed()`).

## Device detail page (`dashboard/src/pages/DeviceDetailPage.vue`)

**One continuous scrollable page, not tabs.** Explicitly corrected after an initial tabs-based (`v-if`/`v-else-if`) implementation — user feedback: "it is still supposed to be one page. The links just make it quicker to navigate." Nav order: **Summary → System → Command History → Alerts → Policies → Software → Patches → Services → Memory → Storage → Network → Custom Fields → Security**. All render simultaneously as `<section :id="'ddev-sec-' + name" class="ddev-page-section">` blocks in that same DOM order; the left-nav only scrolls to and highlights a section, it never hides content. See STYLE.md for the section-separation/scroll-spy CSS+JS pattern in full.

**Command History** (new section, placed right after System) — surfaces the `commands` table, which was already being written to on every direct device action (reboot, restart agent, force-update check, install patches, uninstall agent, single-device Quick Job) but had **zero UI surface anywhere** before this: `api.devices.commands.list()` and its backing `GET /:id/commands` route both already existed, unused, since an earlier session. Found via a real support case — an admin queued a `force_update` command via the kebab menu and had no way to tell whether it was working, since direct commands (unlike Jobs) never appear on the Jobs/Automation page by design. Deliberately scoped to **direct commands only** (`jobId IS NULL`, capped at the last 50, newest first) — commands dispatched as part of a Job already have full visibility on that Job's own detail page (`JobDetailPage.vue`), and including them here too would make the list grow unbounded on a device that's part of many recurring jobs. Table + expandable StdOut/StdErr output reuses `JobDetailPage.vue`'s output-expansion pattern (see STYLE.md), with status shown via the page's own existing `.inv-badge-{ok,warn,danger,muted}` family (`completed`→ok, `sent`→warn, `queued`→muted, `failed`→danger) rather than duplicating `JobDetailPage.vue`'s separate `.jd-status-*` palette. Every direct-command action function (`scheduleReboot`, `restartAgent`, `forceUpdateCheck`, `runAuditNow`, `installApprovedPatches`, `uninstallAgent`) now also calls `loadDeviceCommands()` right after queuing, so the new row appears immediately rather than only on the next full page load.

Fixed one real agent-side bug found while building this: `force_update`'s command handler (`agent/cmd/agent/main.go`) was the one command type that never nudged the check-in loop early (`triggerCheckin`) after finishing, unlike every other handler. Since `updater.ForceCheck()` runs concurrently and can complete its download+verify+swap (which **replaces the running process**, wiping all in-memory state) faster than the next unprompted 60s check-in, the buffered "completed" result for `force_update` almost always lost that race — the command would sit at `status: 'sent'` forever in the dashboard even when the update itself fully succeeded. Confirmed this exact scenario against production D1 directly: a real `force_update` command against a real device (`Nebuchadnezzar`) that genuinely updated it to 0.2.13 within ~3 minutes, still permanently `status: 'sent'`. Fixed by adding the same `select { case triggerCheckin <- struct{}{}: default: }` nudge every other handler already has — not a complete fix for the underlying race (the update could still theoretically win it), but check-in is a small, fast POST that should reliably beat a multi-second binary download+swap in practice. Released in agent v0.2.14.

**Two more small real-usage bugs found and fixed in this same area, later the same session**: (1) the 30s poll `DeviceDetailPage.vue` already had for the core device row (`loadDevice`) never also refreshed Command History (`loadDeviceCommands`) — a `queued`/`sent` command's status looked permanently stuck until a manual full page reload, even though it had actually completed; the poll now refreshes both. (2) `DevicesPage.vue`'s pending-device row only ever offered "Approve" — there was no way to decline/remove a pending device without first navigating into its detail page and using the unrelated "Delete Device" action there (which already works fine for this — `DELETE /v1/admin/devices/:id` has no status guard at all). Added a "Decline" button directly on the pending row (`decline()`, a plain `api.devices.delete()` call, same "no confirm() dialog" convention "Delete Device" already established) so rejecting a mistaken/duplicate enrollment doesn't require leaving the Device Approvals list.

**Change Log is no longer part of this nav** — originally matched Datto's device page nav exactly (ending in Change Log), but was un-inlined into its own dedicated page (`DeviceChangeLogPage.vue`, `/devices/:id/change-log`) once the inline section's lack of pagination/filtering became a real scaling problem (`device_audit_changes` grows unbounded, one row per detected change per audit). const expanded = reactive<Record<string, boolean>>({});
```typescript
function toggleExpand(id: string) {
  if (expanded[id]) delete expanded[id];
  else expanded[id] = true;
}
```

### `loading` ref must start `true` on an edit page, not `false`

Real bug, found from a user report (a visible "blank policy for half a second, then flickers, then the real options show" on `PatchPolicyFormPage.vue`), then found to be copy-pasted across all five full-page edit forms (`PatchPolicyFormPage.vue`, `PolicyFormPage.vue`, `MaintenancePolicyFormPage.vue`, `ComponentFormPage.vue`, `GroupFormPage.vue`). Each declared `const loading = ref(false)`, then ran a few preliminary `onMounted` fetches (companies/devices/groups/timezone — data the form's own flyouts need, not the record being edited) sequentially with individual `try {} catch {}` blocks, and only set `loading.value = true` *after* those finished, right before fetching the actual record. Since Vue renders once synchronously before `onMounted`'s async body starts making progress, `loading` was still `false` during that entire preliminary-fetch window — the form rendered with blank/default values first, then flipped to "Loading…" once `loading.value = true` was finally reached, then flipped back once the real record arrived. Three renders, two of them visible flickers, for what should be one.

Fixed two ways, together:
```typescript
// 1. Initialize loading from isNew, not a bare false, so an edit page never
//    gets that first blank-form render at all.
const loading = ref(!isNew.value);
```
```typescript
// 2. Parallelize the preliminary fetches (they don't depend on each other)
//    instead of sequential awaits, shortening the loading window itself.
onMounted(async () => {
  const [companiesRes, devicesRes, groupsRes] = await Promise.allSettled([
    api.companies.list(), api.devices.list(), api.groups.list(),
  ]);
  if (companiesRes.status === 'fulfilled') companies.value = companiesRes.value;
  if (devicesRes.status === 'fulfilled')   devices.value   = devicesRes.value;
  if (groupsRes.status === 'fulfilled')    groups.value    = groupsRes.value;
  // ...then the real record fetch, gated on !isNew.value as before -- no
  // need to set loading.value = true again, it's already true from init.
});
```
`Promise.allSettled` (not `Promise.all`) to preserve each fetch's original independent "swallow failure, leave the array empty" behavior — a single failed preliminary fetch (e.g. Groups) shouldn't block the others from populating.

Verified live with Playwright against a real local `wrangler dev`, not just reasoned through: intercepted the relevant API calls with an artificial 400ms delay (to reproduce the user's real-world latency window) and sampled the DOM every 100ms through the whole load. The old code showed the bug exactly as described — empty-valued Name input for ~1.3s, then "Loading…" for ~400ms, then the real value — confirming both the root cause and that this test methodology actually detects it (a real control, not just a clean run). The fixed code showed only "Loading…" throughout, transitioning directly to the fully-populated form with zero blank frames.

### Scroll-spy nav (one-page-with-anchor-nav, e.g. DeviceDetailPage)
`IntersectionObserver` with a thin top-of-viewport detection band, rooted at `.page` (the app's real scroll container, not `window` — see STYLE.md):
```typescript
scrollSpy = new IntersectionObserver((entries) => {
  const visible = entries.filter(e => e.isIntersecting);
  if (visible.length === 0) return;
  const topMost = visible.reduce((a, b) => a.boundingClientRect.top <= b.boundingClientRect.top ? a : b);
  activeSection.value = topMost.target.id.replace('ddev-sec-', '');
}, { root, rootMargin: '-16px 0px -70% 0px', threshold: 0 });
```
Deliberately doesn't touch the URL/`route.query` on scroll — only an explicit nav-item click does that (via `router.replace`), so casual scrolling doesn't spam browser history.

**Bottom-of-scroll edge case** (found via real Playwright scroll testing, not obvious from reading the code): a short trailing section (e.g. "Change Log") can lose the "topmost visible" tie-break to a taller preceding section even once you've scrolled all the way down, because both still overlap the detection band simultaneously. Same edge case Bootstrap's own scrollspy special-cases. Fix: check `root.scrollTop + root.clientHeight >= root.scrollHeight - 2` and force the *last* section active when true — both inside the IntersectionObserver callback (covers most real scrolling) **and** in a separate `scroll` listener deferred one macrotask via `setTimeout(fn, 0)` (covers the remaining case where the final scroll increment doesn't change any element's `isIntersecting` state at all, so the IO callback never fires for it). The `.page` element is the app-wide persistent scroll container (outlives any one page component across navigations) — remove the `scroll` listener explicitly in `onUnmounted`, don't rely on the component unmounting to clean it up.

1. Monitors accumulate in local `ref<LocalMonitor[]>` — no API calls until Save

### New-vs-existing nested resource: defer-and-batch, or hit immediately
The general form of the pattern above, now established across five independent instances (`ComponentFormPage.vue`'s Companies and Variables, `PolicyFormPage.vue`'s Monitors and Device Groups, `GroupFormPage.vue`'s Members) — reuse this shape rather than re-deriving it for the next nested many-to-many relationship:
- **On a `/new` page** (`isNew.value` true, no parent id yet): every add/remove/edit of the nested items is a purely local array mutation, zero API calls. On Save: POST the parent first, then loop the accumulated local items into their own `POST`s, then navigate away.
- **On an edit page** (`isNew.value` false, real parent id in hand): every add/remove/edit of a nested item hits its own API endpoint immediately — no separate "Save" step for that sub-resource, since there's already a stable parent id to attach it to.
- A `removeAll`-style bulk action still loops individual `DELETE`s in this convention (best-effort — swallow per-item errors and keep clearing locally) rather than requiring a dedicated bulk-delete endpoint, since these lists are small (self-hosted scale).

2. `LocalMonitor` interface — new fields prefixed by check type (e.g. `pingTarget`, `pingCount`)
3. `monPanel.form` defaults, `openAddMonitor()` reset, `openEditMonitor()` populate
4. `buildConfig()` — maps form fields → the JSON `config` blob
5. `onMounted`'s config-parse block — maps `config` blob back → form fields (mirror of #4)
6. A `xSummary(m)` helper + its case in `monitorSummaryLocal()`'s switch
7. Matching `checkLabel`/`monitorSummary` cases in `GlobalPoliciesPage.vue` (same summary logic, duplicated by design — not shared, matches this file's existing duplication convention)
8. A new `.chip-{type}` CSS color in both `PolicyFormPage.vue` and `GlobalPoliciesPage.vue` — check existing chips before picking a color, the palette is now 10 colors deep (see STYLE.md)
9. New UI block (`v-if="monPanel.form.checkType === 'x'"`) inserted before the shared `mf-pair` (period/interval/priority)

**Type-specific side effects on switching type**: the type-card click handler is `selectCheckType(ct)`, not an inline `@click` assignment — use it to force config field values that don't make sense for a given type (e.g. `software` forces `sustainedMinutes = 0` and `autoResolve = false` when selected, since that type doesn't support either).

**Optional numeric fields use a checkbox that toggles `null`, not a separate boolean flag**: e.g. ping's packet-loss/latency conditions —
```html
<input type="checkbox" :checked="form.x !== null" @change="form.x = ($event.target as HTMLInputElement).checked ? DEFAULT : null" />
<div v-if="form.x !== null"><input v-model.number="form.x" .../></div>
```
`null` in the saved config means "this condition is disabled," not zero.

**Hiding shared fields that don't apply to a type**: wrap the irrelevant fields in `<template v-if="...">` inside `mf-pair` rather than hiding the whole block, since e.g. `software` hides period+interval but still needs the priority selector alongside them in the same flex row.
